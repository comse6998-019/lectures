\section{ReAct: reactive agents}
\label{sec:reactive}

The fixed workflow of \cref{sec:fixed} reads only what its designer scheduled, so it cannot respond
to evidence that the designer did not foresee. The reactive loop removes this limit by letting the
model choose the next action after each tool result, while the agent, the alert and the tools stay
the same as in \cref{sec:fixed}. We define the loop, show how it is built as a graph, and identify
who decides each step. We then compare its gains and costs with those of the fixed workflow, review
published evidence on where such agents fail, and describe the two stops that the runtime adds.

\subsection{What a reactive loop is}
\label{sec:reactive-loop}

A \textbf{reactive loop} is an architecture in which the model selects the next action from the
percepts so far, and the runtime returns an observation that the next selection reads
\citep[\S2]{yao2023react}. The percepts so far are everything the agent has received during the run,
such as the alert, file excerpts and search results. As in \cref{sec:agents-msa}, the runtime is
the code that runs the agent, and an observation is the result of one tool call as the runtime
records it, for example the lines that a file read returned.

The runtime keeps the \textbf{run's state}, the record of the run so far, which
\cref{sec:agents-picture} called the agent's working state: the messages exchanged with the model,
the observations, the number of model calls and the run's status. The
\textbf{status} records whether the run is still running and, if it has ended, how it ended. The
loop proceeds in turns. A \textbf{turn} is one pass through the loop, from one model call to the
next. Every turn consists of the same four steps:
\bi
\item \textbf{Decide.} The runtime makes one model call. A model's \textbf{context} is the input it
receives in one call, and in the loop it holds everything that has happened so far in the run. The
model reads its context and returns a reply that contains its next action: a tool call, a passage
of reasoning that ReAct calls a thought, or both. A \textbf{tool call} is a request to run one of the agent's tools, such as
\demoref{read\_file}, with arguments.
\item \textbf{Dispatch.} The runtime checks the tool call against the tool's \textbf{signature}, the
name and the arguments of the tool as we wrote them, and then executes the tool. A malformed call,
for example one that names a tool that does not exist, is returned to the model as an observation
that describes the error. The run continues instead of crashing. Lecture~4 studies this check in
detail.
\item \textbf{Observe.} The runtime writes the tool's result into the run's state as an
observation, and the model never writes one. This division matters for security. The model can
write text that looks like a tool result, but such text never becomes an observation.
\item \textbf{Route.} A predicate that we wrote selects what happens next: another turn, a
submission or the end of the run. As in \cref{sec:fixed-decisions}, a predicate is a condition in
code, here evaluated over the run's state.
\ei

In the graph of the loop (\cref{sec:reactive-graph}), the routing predicate runs right after the
model call, because what it tests is the model's reply. When the reply contains a tool call, the run
moves on to the dispatch and observe steps. Once the observation is written, the run returns to the
model unconditionally.

ReAct, the published method that this loop follows, rests on one idea: language is part of the
action space. An agent's \textbf{action space} is the set of actions it can choose from. Without
language, the action space of our agent would contain only its tool calls. ReAct adds a second kind
of action, the \textbf{thought}: a piece of text in which the model reasons about the task. In our
running example, a thought might note that the flagged query relies on a helper file, and that this
helper should be read before the patch is written.

A thought is an action, but it acts on nothing outside the model's context. It changes the context
that the next decision reads, and it leaves the files, and every other part of the environment,
unchanged. A tool call, in contrast, either gathers information from the environment, as
\demoref{read\_file} and \demoref{search} do, or changes it, as \demoref{edit} does. Because a
thought stays in the context, the reasoning it records is available to every later decision in the
run.

A thought can appear in the same reply as a tool call. A reply that contains a thought and no tool
call is routed to submit, because the absence of a tool call is the model's signal that it has
finished (\cref{sec:reactive-edge}).

\subsection{The graph of the loop}
\label{sec:reactive-graph}

We build the reactive loop as a graph of three nodes whose edges decide what runs next. As in
\cref{sec:agents-msa}, each state of \msa{}'s state machine becomes a node, and each transition becomes
an edge. In code, a node is a function that reads and updates the run's state, and an edge connects
a node to another node that may run after it. The word state is used in three ways in these notes.
The state of the environment is everything about the world that can matter to the task
(\cref{sec:agents-properties}). The Controller, Tool and Submit states are modes of the state
machine. The run's state is the record of the run that every node reads and writes.
\Cref{fig:reactive-loop} draws the graph, and its nodes are the
following:
\bi
\item \textbf{\demoref{controller}.} This node is the only place where the model is called. Each
visit makes one model call, unless one of the runtime's stops (\cref{sec:reactive-stops}) ends the
run before the call is issued.
\item \textbf{\demoref{tools}.} This node checks the requested tool call, executes it and writes the
observation.
\item \textbf{\demoref{submit}.} This node runs three mechanical checks on the patch: that it
applies, that it touches the flagged line, and that a rescan no longer reports the alert.
\ei

\begin{figure*}[t]
  \centering
  \includegraphics[width=\textwidth,trim=0 38 0 0,clip]{figures/deck/reactive-loop.png}
  \caption{The graph of the reactive loop. Only the controller node calls the model. Solid edges
  are always taken, and dashed edges are taken when a predicate over the run's state selects them.
  The grey labels \emph{by the model} and \emph{by the runtime} name who supplies the value that
  selects an edge. The solid edge from tools back to controller makes the program a loop.}
  \label{fig:reactive-loop}
\end{figure*}

The nodes do the work of a run, and the edges decide which node runs next. The architectures in
these notes differ in who decides what runs next (\cref{sec:fixed}), so the edges are the part of the
graph that distinguishes one architecture from another.

The graph has two kinds of edge. An \textbf{unconditional edge} is taken every time the run reaches
its source node, and the figure draws it solid. A \textbf{conditional edge} is taken only when a
predicate over the state selects it, and the figure draws it dashed.

There are two unconditional edges. The first, from Start to \demoref{controller}, means that every
run begins with a model call. The second, from \demoref{tools} back to \demoref{controller}, is a
\textbf{back edge}: an edge that leads from a node to an earlier node of the graph, so that the
graph contains a cycle and a run can return to a node it has already visited. This back edge
returns every observation to the model, which then chooses the next action. The conditional edges
are the following:
\bi
\item \textbf{Tool call.} From \demoref{controller} to \demoref{tools}, when the model's reply
contains a tool call.
\item \textbf{No tool call.} From \demoref{controller} to \demoref{submit}, when the model's reply
contains no tool call.
\item \textbf{Stopped.} From \demoref{controller} to the end of the run, when the runtime has
stopped the run because the budget is exhausted or the run is making no progress
(\cref{sec:reactive-stops}).
\item \textbf{Accepted.} From \demoref{submit} to the end of the run, when the checks accept the
patch.
\item \textbf{Rejected.} From \demoref{submit} back to \demoref{controller}, when the checks reject
the patch. The rejection reaches the model as feedback. This edge is the loop's second back edge.
\ei

The back edge from \demoref{tools} to \demoref{controller} is what makes the program a loop. Without it, the model would never see the result of
a tool call, so it could not choose its next action based on what it had read. Like the chain, the
fixed-workflow version of \msa{} (\cref{sec:fixed}), the agent could then never choose a read in
response to an earlier one.

In code, each edge is declared with one call (\cref{lst:reactive-edges}). The names
\demoref{START} and \demoref{END} stand for the beginning and the end of the run. The first two
lines declare the unconditional edges, and the second of them is the back edge from \demoref{tools}
to \demoref{controller}. Deleting that single line would end the loop through the tools, so the
model could no longer respond to what it reads.

\begin{lstlisting}[basicstyle=\ttfamily\footnotesize, caption={Illustrative code that declares the edges of the reactive loop and compiles the graph.}, label=lst:reactive-edges]
graph.add_edge(START, "controller")
graph.add_edge("tools", "controller")   # the back edge

graph.add_conditional_edges("controller", after_controller,
    {"tools": "tools", "submit": "submit", END: END})
graph.add_conditional_edges("submit", after_submit,
    {"controller": "controller", END: END})

app = graph.compile()
\end{lstlisting}

\subsection{Conditional edges and compilation}
\label{sec:reactive-code}

A conditional edge chooses the next node from a fixed list of successors. The \textbf{successors} of
a node are the nodes that may run after it. We list them when we build the graph, and nothing that
happens during a run can add to the list.

In \cref{lst:reactive-edges}, each call to \demoref{add\_conditional\_edges} has three parts: a
source node, a \textbf{routing function}, and a dictionary. The routing function reads the state and
returns a key. The dictionary maps each key to the node that runs next.

The successors of \demoref{controller} are \demoref{tools}, \demoref{submit} and the end of the run.
The successors of \demoref{submit} are \demoref{controller} and the end of the run. Each entry in a
dictionary appears as one dashed edge in \cref{fig:reactive-loop}, so three dashed edges leave
\demoref{controller} and two leave \demoref{submit}.

Because the routing function returns a key rather than a node, it cannot send the run to a node we
did not list. Whatever key it returns, the run can only move to a node named in the dictionary, and
a key that is not in the dictionary causes an error. When we say that the model chooses what happens
next, we mean something narrow: it chooses among successors we named in advance.

Once the nodes and edges are declared, the graph is \textbf{compiled}, that is, turned into a
runnable object (the last line of \cref{lst:reactive-edges}). Compilation happens once, before the
program reads any alert, and the same compiled object runs every alert.

A \textbf{path} is the sequence of nodes that one run actually visits. Two runs that take different
paths still run the same compiled graph. Their paths differ because the predicates evaluate to
different values on different states: for example, the model requests a tool in one run and submits
in the other. The structure of the graph does not change during a run or between runs.

If we want runs to behave differently in some situation, we do not rebuild the graph between runs.
We add a predicate that tests for that situation and write it into the graph before it is compiled.
The compiled graph then stays the same from one run to the next.

\subsection{Who picks the edge}
\label{sec:reactive-edge}

The model selects the node that follows \demoref{controller} in exactly one way: by including a tool
call in its reply, or by leaving it out. The routing function after \demoref{controller} shows this
mechanism. In code, it looks like this (\cref{lst:reactive-after-controller}):

\begin{lstlisting}[basicstyle=\ttfamily\footnotesize, caption={Illustrative code for the routing function after the controller node.}, label=lst:reactive-after-controller]
def after_controller(state) -> str:
    if state["status"] != RUNNING:
        return END
    if state["messages"][-1].tool_calls:
        return "tools"
    return "submit"
\end{lstlisting}

The function makes two tests, and each tests a value that a different actor supplied:
\bi
\item \textbf{The runtime's test.} Only the runtime writes the status field. If the status is no
longer \demoref{RUNNING}, the runtime has stopped the run (\cref{sec:reactive-stops}), and the
function returns \demoref{END}.
\item \textbf{The model's test.} If the model's last message contains a tool call, the run goes to
\demoref{tools}. Otherwise it goes to \demoref{submit}. A reply without a tool call is the model's
signal that it has finished.
\ei

The model has no other way to choose what happens next. Its text affects routing only through the
presence or absence of a tool call. Every other branch is selected by a value that the runtime
supplies. That value is either the status, when the runtime has stopped the run, or the result of
the submit checks, which decides between acceptance and rejection.

The runtime records each routing decision in the run's \textbf{trace}, the log of events it writes
during a run. The event it writes for a routing decision is a \textbf{routing event}. Each routing
event has a \demoref{by} field that names who supplied the value the predicate tested. It is \demoref{by="model"} when the model's output, a tool call or its absence,
selected the branch. It is \demoref{by="runtime"} when a field the runtime owns selected it, for
example the status set by a stop or the result of the submit checks. In both cases, the predicate
itself was written by us. Reading the \demoref{by} field across a trace shows which decisions in a
run came from the model and which came from the runtime.

\subsection{The model's autonomy increases}
\label{sec:reactive-autonomy}

The reactive loop moves several control decisions from the designer to the model.
\Cref{tab:reactive-autonomy} lists the decisions of a fixed workflow (\cref{sec:fixed}) and shows
who makes each one in the two architectures. In the fixed workflow column, every control decision
is ours and is made at design time. In the reactive loop column, the model makes the decisions about
which operation runs next, whether another runs after it, and which artifacts a step touches. The
last row is a content decision, which the model makes in both architectures.

\begin{table}[htbp]
  \caption{Who makes each decision in a fixed workflow and in a reactive loop. In the reactive loop,
  the model takes over the choice of the next operation, whether another follows, and which
  artifacts a step touches.}
  \label{tab:reactive-autonomy}
  \begin{adjustbox}{width=\linewidth}\begin{tabularx}{\linewidth}{L{0.32\linewidth}L{0.29\linewidth}X}
    \toprule
    \textbf{Decision} & \textbf{Fixed workflow} & \textbf{Reactive loop} \\
    \midrule
    \textbf{Which operation runs next} & Us, at design time & The model, at run time \\
    \textbf{Whether another runs after it} & Us, at design time & The model, until the budget \\
    \textbf{How many model calls} & Us, at design time & Bounded by the budget \\
    \textbf{What ends the run} & Us, at design time & A predicate we wrote \\
    \textbf{Which artifacts a step touches} & Us, at design time & The model, by using tools \\
    \textbf{What a model call returns} & The model & The model \\
    \bottomrule
  \end{tabularx}\end{adjustbox}
\end{table}

Each row has the following meaning in the loop:
\bi
\item \textbf{Which operation runs next.} The model chooses it at run time by deciding whether to
call a tool and which one.
\item \textbf{Whether another runs after it.} The model keeps the run going by requesting further
tools, until it stops requesting them or the budget is exhausted.
\item \textbf{How many model calls.} Nobody fixes the number in advance. The budget we set only
bounds it from above.
\item \textbf{What ends the run.} A predicate we wrote ends the run, as in the fixed workflow.
\item \textbf{Which artifacts a step touches.} The model chooses them through the arguments of its
tool calls, for example which file to read or which lines to edit.
\item \textbf{What a model call returns.} The model still decides it.
\ei

Even where the model gained a decision, it chooses among options we defined. We still write the tool
signatures, the \textbf{state schema} (the fields the state contains and their types), the routing
predicates and the budget. The model selects its next action from a set of options we fixed in
advance. A reactive loop is still a program that we write. What we no longer write down is the order
of its operations.

An agent lacks autonomy to the extent that it relies on its designer's prior knowledge rather than
on its own percepts (\cref{sec:fixed-autonomy}). By this measure, the reactive loop is more
autonomous than the fixed workflow in the decisions the model has taken over. The choice of the next
action, for example, now relies on the agent's percepts, the results it has observed during the run,
rather than on the designer's prior knowledge alone. The decisions that remain ours, such as the
budget and what ends the run, still rely on prior knowledge.

\subsection{What the loop gains}
\label{sec:reactive-gains}

Letting the model choose the next action gives the agent three benefits, which we call reach,
proportion and recovery:
\bi
\item \textbf{Reach.} The agent can take an action whose purpose is to gather information, and then
use what it learned in its next decision. Suppose the flagged line calls a helper function defined
in another file. The model can read that helper and only then decide how to patch. The chain has no
step in which to make this choice, because its reads were scheduled before the run.
\item \textbf{Proportion.} The cost of a run follows the difficulty of the alert. An easy fix takes
only a few turns, and a hard one takes more. The chain makes the same number of model calls for
every alert, so an easy alert costs as much as a hard one.
\item \textbf{Recovery.} An unhelpful observation is not final, because there is a next turn in
which to try something else. For example, a search that returns nothing can be followed by a
different search.
\ei

All three benefits come from a single change to the graph: the back edge from \demoref{tools} to
\demoref{controller}. Because of that edge, the model sees each tool result and chooses the next
action. No new node is needed to give the agent a second look, a cost that grows with the difficulty
of the task, or a way to recover from an unhelpful result.

The chain has no such edge. If its single read returns the wrong part of the code, the error passes
unchanged through every later step and into the patch.

\label{sec:reactive-costs}

The reactive loop gives up the three guarantees of the fixed workflow, shape, address and
termination (\cref{sec:fixed-guarantees}). They are lost together, because each of them depended on
the designer fixing the order of the steps before the run:
\bi
\item \textbf{Shape.} In a fixed workflow, the number and order of model calls are known before the
run. In the loop, the number of model calls depends on the model's choices, so we cannot know the
cost of a run before it starts. The budget gives only a worst case. It is an upper limit and not an
estimate, so for each alert we must reserve the cost of the whole budget, however few calls the
alert turns out to need.
\item \textbf{Address.} In a fixed workflow, a wrong result can be traced to the step that produced
it. In the loop, a failure is spread over many turns, each of which looks reasonable on its own.
Finding the turn where the run went wrong means reading the whole trace.
\item \textbf{Termination.} In a fixed workflow, the run ends when its last step returns. The loop
has no last step. A run ends when a predicate we wrote ends it: either the submit checks accept a
patch, or a limit we imposed, such as the budget, stops the run. A run stopped by a limit ends
without an accepted patch. It has stopped, but it has not finished.
\ei

The three losses share one missing capability: the loop has no measure of progress.
\textbf{Progress} here means movement toward an accepted patch. The loop cannot tell a turn that
advanced the investigation from a turn that wasted a model call. Apart from the stall check
(\cref{sec:reactive-stops}), which notices only results that repeat exactly, the only thing the
runtime measures about a run is the number of model calls it has made, and the budget is a limit on
that number. A run that reaches the budget has paid for every model call it was
allowed and still ends without an accepted patch.

A plan would give the run a target against which each turn can be measured. The planner and the
validator are designed to supply this missing capability (\cref{sec:planning,sec:validation}).

\subsection{Where the failures occur}
\label{sec:reactive-failures}

In a published study, a fixed workflow and two reactive loops failed at different stages of a run
\citep{liu2025issuefailures}. The study, available as a preprint, examined 150 issues on which at
least one of three issue-solving tools failed, programs that take an issue report and a repository
and try to produce a patch.
The failures come from runs on SWE-bench Verified, a benchmark of software issues of the same kind
as SWE-bench Lite (\cref{sec:fixed-agentless}). Each failure was annotated by hand with the stage of
the run in which it appears.

All three tools used the same \textbf{backbone model}, the language model that a tool calls to make
its decisions. One tool, Agentless-1.5, is a fixed workflow. The other two, OpenHands-CodeAct-2.1
and Tools + Claude 3.5 Sonnet, are reactive loops. \Cref{tab:reactive-failures} gives, for each
tool, the stage the study associates with its failures and the share of that tool's own failures
found at that stage. Each share is a fraction of one tool's failures, not of all issues.

Agentless-1.5, a version of the Agentless workflow of \cref{sec:fixed-agentless}, fails most often
at its first decision. Just over half of its failures (51.3\%) involve an error in localization, the
first phase, which decides where in the code to edit. No later phase revisits that decision, so the
rest of the run builds on a mistake it cannot detect.

About half of each reactive loop's failures appear in the study's iteration and validation stage,
which covers the repeated turns that the model drives. The fixed workflow has no such stage, because
its phases run once, in an order its designers fixed. Agentless does validate its patches, but in
one fixed phase that the model does not direct. The mechanism that gives the loop reach, proportion
and recovery is also where its new failures occur.

The comparison is descriptive. Holding the model fixed removes one source of variation, but the
tools also differ in their prompts and their interfaces. The study therefore does not show that the
architecture alone causes the difference. It also does not show which tool fails more often, because
each share is a fraction of a single tool's failures. What it shows is where each tool's failures
occur.

\subsection{Shapes of failure inside the loop}
\label{sec:reactive-shapes}

In the same study, roughly 65\% of the failures trace back to flawed reasoning by the model, for
example persisting with an approach that keeps failing \citep{liu2025issuefailures}. The study also
names the failure modes it found at each stage. We call the following failure modes of the
iteration and validation stage, where about half of each reactive loop's failures appear,
\textbf{failure shapes}. The term is unrelated to the shape guarantee of \cref{sec:fixed-guarantees}. Each
failure shape motivates a mechanism that we study later:
\bi
\item \textbf{Non-progressive iteration.} The agent generates nearly identical patches again and
again, with trivial differences, while the defect remains. The loop keeps running without getting
closer to a fix. A plan addresses this shape by giving the run a target against which each turn can
be measured (\cref{sec:planning}).
\item \textbf{Validation retreat.} The agent edits the failing test instead of the code, so that the
test passes while the defect remains. The component that proposed the patch has, in effect, graded
its own work. A validator addresses this shape by giving the decision to accept a patch to a
component that did not write it (\cref{sec:validation}).
\item \textbf{Context amnesia.} The agent loses track of the original objective over a long
interaction. Lecture~3 proposes a reflection step for this shape. After the validator rejects a
patch, the step writes a description of what went wrong, and a new attempt starts. The new attempt
clears the plan and the patch but keeps that description.
\ei

In general, the loop cannot detect any of these shapes while it runs, because it has no measure of
progress (\cref{sec:reactive-costs}). The stall check (\cref{sec:reactive-stops}) catches only one
narrow form of non-progressive iteration, the form in which the results repeat exactly.

The study also measured how long the runs of the two reactive loops last. Failed runs take on
average about 3.5 times as many steps as successful ones, and the study links this to failures that
trap the agent in a loop. The study counts run length in \textbf{rounds}, where a round is one turn
of the loop. For OpenHands-CodeAct-2.1, 80\% of the successful runs end within 25 rounds, but 54
rounds pass before 80\% of the failed runs have ended. Failed runs therefore last longer and
consume more of the budget.

These counts can be computed only after the runs have ended, when we know which runs failed. During
a run, the loop has no signal that separates a run heading toward an accepted patch from a run that
repeats itself without progress.

\subsection{The two runtime stops}
\label{sec:reactive-stops}

Because the loop cannot recognize a failing run, the runtime has two stops. A \textbf{stop} is a
check in the runtime that ends a run when its condition holds, whatever the model would do next. We
write both stops, and the \demoref{controller} node checks both before it issues the model call. In
code, the two checks look like this (\cref{lst:reactive-stops}):

\begin{lstlisting}[basicstyle=\ttfamily\footnotesize, caption={Illustrative code for the two stops, at the start of the controller node.}, label=lst:reactive-stops]
if state["model_calls"] >= budget:          # budget = 40
    return {"status": BUDGET_EXHAUSTED}
if stalled(state["observations"], limit=3):
    return {"status": NO_PROGRESS}
# ... only now is the model called
\end{lstlisting}

The two stops work as follows:
\bi
\item \textbf{The budget.} When the number of model calls in the run has reached the budget, 40 in
our agent, the run ends with the status \demoref{budget\_exhausted} (the constant
\demoref{BUDGET\_EXHAUSTED} in the code).
\item \textbf{The stall check.} When the last three observations are identical, the run ends with
the status \demoref{no\_progress} (\demoref{NO\_PROGRESS} in the code). The function
\demoref{stalled} makes this comparison, and \demoref{limit=3} sets how many observations it
compares.
\ei
Each stop sets the status field, and the routing function after \demoref{controller}
(\cref{lst:reactive-after-controller}) then sends the run to its end.

The checks run before the model call so that they act as controls. A check is a \textbf{control}
when it prevents an unwanted outcome, here a model call beyond the limit. A check placed after the
call would detect that a limit had been passed only once the extra call had been made and paid for.
It would record the overrun instead of preventing it, so it would be a report after the fact rather
than a control.

The stall check is placed before the call for the same reason: a run that has stopped making
progress ends before it pays for another model call. Because the budget check runs before the call,
a run never makes more model calls than the budget allows. A run stopped by the budget records no
further model call after its last routing event.

The stall check compares results rather than calls. A simpler rule would stop the run when the model
repeats the same call, but the two rules are not equivalent. A model that changes its
\demoref{search} pattern slightly on each attempt never repeats a call, yet it can make no progress
at all. For example, a model that tries six different search patterns, each of which returns no
matches, never repeats a call. A same-call rule would not stop it, and only the budget would end its
run. Every one of those searches returns the same empty result, which is exactly the condition the
stall check tests.

Comparing results also covers the case of identical calls. The task environment is deterministic, so
identical calls on files that have not changed return identical results (\cref{sec:agents-properties}).

The stall check has a clear limit. It catches one form of non-progressive iteration, the form in
which the results repeat exactly. A run whose results keep changing, even trivially, is not stopped
by the check. The loop cannot detect the general failure shapes of \cref{sec:reactive-shapes} while
it runs, so such a run, if it never produces an accepted patch, ends only when it reaches the
budget.

\subsection{An example run}
\label{sec:reactive-run}

An example run of the loop on the worked alert shows the four steps of a turn, and the benefits of
reach and proportion, in practice. The alert flags a SQL query built by string interpolation
(\cref{sec:agents-run}). In each of the first three turns, the model requests a tool, the runtime
executes it and writes the result as an observation, and the run returns to the model. The run
takes four turns:
\be
\item The model reads the region of the flagged file around the alert.
\item The model reads a helper file that the flagged query uses, which the alert does not name.
This is reach: the chain, which reads only the region around the flagged line, could not have
chosen this read. The run in \cref{fig:agents-run} did not make this read, because two runs on the
same alert can take different paths (\cref{sec:agents-properties}).
\item The model edits the flagged file so that the query text contains a placeholder and the value
is passed separately as a bound parameter.
\item The model replies without a tool call, which signals that it has finished. The
\demoref{submit} node runs its checks: the patch applies, it touches the flagged line, and the
rescan is clean. The runtime ends the run with the status \demoref{accepted}.
\ee

The run was accepted after four model calls against a budget of 40, so neither stop was close to
ending it. This is proportion: an easy fix took only a few turns. The model made every routing
decision in the run except the last: it requested a tool in the first three turns and replied
without one in the fourth. The runtime made the last decision, the acceptance.

\subsection*{Key points}
\bi
\item A reactive loop lets the model choose the next action after each observation, and every turn
has four steps: decide, dispatch, observe and route.
\item ReAct makes language part of the action space: a thought is an action that changes only the
model's context, while a tool call reads or changes the environment.
\item The loop is one graph, compiled once, in which each conditional edge chooses among successors
fixed when the graph is built, and different runs take different paths because the predicates
evaluate differently on different states.
\item The model chooses the next node only by including a tool call in its reply or leaving it out,
and the runtime supplies the value that selects every other branch.
\item The back edge from tools to controller creates the loop and gives it reach, proportion and
recovery, and the loop loses shape, address and termination because the order of its steps is no
longer fixed before the run.
\item In a study with one backbone model, about half of the fixed workflow's failures appeared at
localization and about half of each reactive loop's in iteration and validation, but the study does
not show that architecture is the cause.
\item The runtime checks its two stops, the budget and the stall check, before each model call so
that they prevent an unwanted call instead of recording it, and the stall check catches only the
non-progressive iteration whose results repeat exactly.
\ei

\section{What connects one step to the next}
\label{sec:state}

\subsection{Storing the state machine's variables}
\label{sec:state-transition}

The machine diagram shows which step may follow another. A shared state record holds the
information those steps pass to one another. Routing and dispatch, discussed later, also use
this record.

A configuration has two parts: the control location and the values of the variables
(\cref{def:configuration}). The runtime represents these parts separately. The state record
holds the variable values, while the runtime tracks which step runs next. A \emph{state schema}
specifies the name and type of each field in the record. Each step reads the record and returns
updates for the fields it changes. In our code, \demoref{StateGraph(AgentState)} creates a graph
that uses \demoref{AgentState} as its schema.

Updating state involves two operations. First, a node reads the current state $s_t$, obtains an
external result $e_t$, and returns a partial update $u_t$. The runtime then combines that update
with the stored state, one field at a time:
\[
  u_t \;=\; \mathrm{node}(s_t,\, e_t), \qquad
  s_{t+1} \;=\; \mathrm{merge}(s_t,\, u_t).
\]
Here $e_t$ represents a model reply or tool observation obtained while the node runs. In the
code, the node receives state as its argument and obtains this external result itself. Any field
missing from the update keeps its previous value in $s_{t+1}$.

A node can return just the fields it updates. As the LangGraph documentation states,
``the Node does not need to return the whole State
schema - just an update''~\citep{langgraph-graph-api}. After a model call, our controller returns
three of the loop's ten fields: \demoref{messages}, \demoref{model\_calls} and \demoref{usage}.
Either of its two early-stop paths returns only \demoref{status}
(\cref{fig:controller-update}).

The runtime applies each field's merge rule and stores the result. The node therefore returns
its contribution, while the merge rule determines whether to append it, add it to a total or
replace the previous value.

\subsection{Model context, runtime state, durable state}
\label{sec:state-three}

The information available to a model call overlaps with the information retained by the
runtime. The model receives the instructions and data assembled for that call. The runtime also
keeps counters and other fields used to control execution. State is \emph{durable} when it is
saved beyond the life of the process; resuming a run requires enough saved information to
continue from the stopping point.

\begin{table}[htbp]
  \centering
  \begin{adjustbox}{width=\linewidth}\begin{tabularx}{\linewidth}{@{}L{0.19\linewidth}X@{}}
    \toprule
    \textbf{Record} & \textbf{What it holds, and who reads it} \\
    \midrule
    Model context & Instructions, selected history and observations sent in one model call.
    Different model roles can receive different contexts. Our controller receives the
    conversation; the plan node and validator receive inputs prepared for their roles. \\
    Runtime state & The record available between steps. It includes fields that are never sent
    to the model. Nodes, routing functions and limit checks read it. \\
    Durable state & State saved so that it remains available after the process ends. To resume
    a run, the saved record must also correspond to the external state, such as workspace
    files, and identify pending work. \\
    \bottomrule
  \end{tabularx}\end{adjustbox}
  \caption{Three kinds of record. Each call's model context is derived from runtime state.
  Durable state is runtime state saved beyond the process lifetime.}
  \label{tab:state-three}
\end{table}

Counters provide an example of information the runtime uses without sending it to the model.
Our loop refuses a model call when \demoref{model\_calls} reaches forty, or when the last three
observations are identical. The model receives neither limit. The runtime enforces them by
checking the state before the call. Including a limit in a prompt would not replace this check.

If our agent's process stops during a run, a new process cannot recover the state held in its
memory. Neither graph uses a checkpointer to save that state. Trace files and workspace files
may remain, but they are insufficient to resume the run. LangGraph allows a graph to use a
checkpointer, which gives ``agents short-term
memory'' and ``lets LangGraph applications keep useful information beyond a single graph
run''~\citep{langgraph-persistence}. Our JSONL trace contains selected events
(\cref{sec:efsm-traces}). \textbf{The saved trace does not contain enough information to resume
the run.}

Saving state does not by itself prevent repeated work after a restart. The runtime may need to
rerun an interrupted node from the last saved point. That node could repeat a file change or a
paid call if its completion was not saved. The amount of repeated work depends on where the
runtime places checkpoints and task boundaries. Later units examine these recovery requirements.
Here we focus on the state needed while a run is executing.

\subsection{Reducers: combining updates with stored state}
\label{sec:state-reducers}

A field can retain a history, a running total or just its latest value. Its \emph{merge function}
determines how each update changes the stored value, and therefore what later steps can read.

In an extended state machine, a transition's set action assigns values to variables
(\citealp[slide~5]{seshia2015extended}). Our implementation divides this action between the node
and the runtime: the node returns an update, and the runtime combines it with the stored value.

\begin{definition}[Partial update]
\label{def:partial-update}
A partial update is a step's returned contribution to state. It gives values for some fields
and leaves the others unchanged.
\end{definition}

\begin{definition}[Merge function]
\label{def:reducer}
A merge function combines a field's stored value with the value supplied in an update. Its
result becomes the field's new value. If no merge function is specified, the update replaces
the stored value.
\end{definition}

LangGraph calls the merge function a \emph{reducer}. We use that term from here on. A reducer
takes two arguments, \demoref{(current, update) -> new}, and is attached to a field through
\demoref{Annotated[T, fn]}. When a node returns that field, the runtime applies its reducer.
For example, \demoref{add\_messages} appends new messages and replaces an existing message when
an update uses the same identifier. Other functions of two arguments can also serve as
reducers, including Python's \demoref{operator.add} and functions defined in our code.

Most fields use one of three merge rules.

\bi

\item \textbf{Append.} Add the new entries to the end of the stored list. Keeping earlier entries
allows later steps to examine a sequence, such as checking whether the same result appeared
three times in a row. Keeping only the latest result would lose that information.

\item \textbf{Replace.} Store the new value in place of the previous one. This default rule suits
fields such as the current plan, decision or status, where later steps need the latest value.

\item \textbf{Accumulate.} Combine the new contribution with the stored value, usually by
addition. Each node reports only its own contribution, such as the cost of its model call.
The reducer adds that contribution to the running total.

\ei

The merge rule also determines how to clear a field. Appending an empty list adds nothing:
combining \demoref{[]} with \demoref{[x, y]} still gives \demoref{[x, y]}.
\textbf{An empty update does not clear a list that uses an append reducer.} To clear it, we must
bypass the reducer and replace the stored value. LangGraph provides \demoref{Overwrite} for
this purpose. Recording the reset as a separate trace event makes this exception to the normal
merge rule visible.

\subsection{Field lifetimes}
\label{sec:state-lifetimes}

A reducer specifies how to combine an update with a stored value. We must also decide how long
that value remains valid. Later steps can make wrong decisions if they rely on an outdated
value.

A field's \emph{lifetime} is the part of a run during which other steps can rely on its value.
It begins when the value is written and ends when an event makes it outdated. The writer must
then replace or clear it. We choose this lifetime when designing the field. The reducer alone
cannot enforce it; the nodes that write the field must update or clear it at the appropriate time.

For each field, identify the step that writes it and the event that makes it outdated. The
following six lifetimes describe common choices.

\bi

\item \textbf{Identity.} Set the field before the run and leave it unchanged. No custom reducer
is needed. Task details, the target and the workspace usually have this lifetime because they
define what the run is doing and where it may act. Changing them would change the task during
execution.

\item \textbf{Run.} Keep the information throughout the run and add to it as work proceeds. A
history uses an append reducer; a running total uses an accumulating reducer. Conversations,
observations, and call or token totals have this lifetime when later steps need the full
history or total.

\item \textbf{Current.} Keep the latest value until the step that writes it supplies a new one.
The default replace rule suits a current plan, candidate, check result or status.

\item \textbf{Handoff.} One node writes information for another node to read once and then clear.
For example, it can record why the planner must revise a plan. Leaving the field set can cause
a later routing decision to act on the same signal again.

\item \textbf{Window.} Keep the full history, but store an index marking where a particular
check should start reading. This lets a check use only recent events while other steps retain
access to earlier ones. Updating the index moves the window without deleting history.

\item \textbf{Attempt.} Keep the value for one attempt and clear it before starting another.
This applies to a failed attempt's candidate and check results when they would mislead the
next attempt. The merge rule must allow clearing: a replacement field can receive an empty
value, while a field with an append reducer needs \demoref{Overwrite}.

\ei

The choice of lifetime matters for counters that enforce limits. A limit covering several
attempts needs a counter that persists for the whole run. \textbf{Resetting a counter after each
failure prevents it from enforcing a limit across attempts.}

\subsection{Invariants}
\label{sec:state-invariants}

A spending limit must hold throughout the run. To prove that it does, we must examine all
transitions that could affect it. Specifying a reducer or lifetime for one field is only part
of that argument.

\begin{definition}[Invariant]
\label{def:invariant}
``An invariant for a state machine is a predicate, $P$, on states, such that whenever $P(q)$ is true
of a state, $q$, and $q \to r$ for some state, $r$, then $P(r)$ holds''~\citep[p.~5]{mit6042-lec16}.
\end{definition}

For an extended state machine, each state in this definition is a configuration $(q, v)$, and
the arrow represents one transition. The proof uses induction: show that the condition holds
at the start, then show that any transition from a configuration satisfying it leads to
another configuration satisfying it. It follows that the condition holds throughout the run.

The second step considers every configuration that satisfies the condition, even those the
program never reaches. Sometimes the property we want is too weak to complete this step. We
then prove a stronger condition that includes it. The following example shows why.

We want to show that \emph{model calls stay within the call budget}. Let $B$ be the budget, $c$
the call count stored by the program, and $k$ the actual number of completed calls. The runtime
can read only $c$. We use $k$ in the proof to describe what actually happened. Our goal is
$k \leq B$. We prove this by also showing that the stored count matches the actual count, using
$P \equiv (c = k \,\wedge\, c \leq B)$. At the start, no call has been made and $c = 0$, so $P$
holds. Each transition must then meet the following conditions.

\bi

\item \textbf{Admission} (\cref{def:admission}). Before a model call starts, the program checks
$c < B$. Since the recorded count matches the actual count, completing one more call increases
$k$ by one without exceeding $B$.

\item \textbf{Counting.} Every completed call adds exactly one to $c$. If a call is omitted,
$c$ falls below $k$, and later admission checks can permit too many calls. Counting a call twice
uses up the recorded budget too early.

\item \textbf{Preservation.} A step that makes no call leaves $c$ unchanged. No step, including
plan revision, decreases it. The count therefore needs the run lifetime described in
\cref{sec:state-lifetimes}. Resetting $c$ after completed calls leaves $c \leq B$ true but makes
$c = k$ false. Later checks can then allow the actual call count to exceed $B$.

\ei

This proof covers completed calls. An exception may interrupt a call after it has incurred a
cost but before it is counted. The condition $P$ does not account for that cost.

An accumulating reducer helps by adding each reported call to $c$. Each node must still check
the budget before calling and report every completed call exactly once. \textbf{The reducer
adds the reported counts; their accuracy depends on the callers.} In our agent, $c$ is
\demoref{model\_calls} and $B$ is forty.

\subsection{State schemas of the loop and the planning agent}
\label{sec:state-demo}

The Python class \demoref{AgentState} defines our schema as a \demoref{TypedDict}
(\cref{fig:agentstate}). Each key names a state field, and its type annotation specifies the
kind of value it holds. Writing \demoref{Annotated[T, fn]} also assigns the reducer
\demoref{fn}. The setting \demoref{total=False} makes every key optional for type checking,
which allows the partial dictionaries returned by nodes. \demoref{TypedDict} supports static
type checking~\citep{pep589}; it does not check values while the program runs.

When we construct \demoref{StateGraph(AgentState)}, LangGraph reads the schema and creates a
channel for each field. A channel stores the value and applies its update rule: the specified
reducer, or replacement by default. We then build the graph using these operations:

\bi

\item \demoref{add\_node(name, fn)} registers a node: a function that receives the whole state and
returns a partial update.

\item \demoref{add\_edge(a, b)} fixes a transition from node \demoref{a} to node \demoref{b}.

\item \demoref{add\_conditional\_edges(a, route, \{...\})} registers a routing function to run after
\demoref{a}. It reads the updated state and returns the next node's name without writing state.

\item \demoref{compile()} checks the graph's connections and returns a runnable graph.
\demoref{invoke(initial\_state(\ldots))} starts the run with a value for every key, so nodes do not
read missing keys.

\ei

\begin{lstlisting}[basicstyle=\ttfamily\scriptsize]
graph = StateGraph(AgentState)
graph.add_node("plan", self.plan)
graph.add_node("tools", self.tools)        # ... and three more
graph.add_edge(START, "plan")
graph.add_conditional_edges("tools", self.after_tools,
                            {"controller": "controller", "plan": "plan"})
graph.add_edge("validate", END)
app = graph.compile()
\end{lstlisting}

The loop's schema (\cref{fig:agentstate}, left) uses three lifetimes. Identity fields identify the
scanner alert, test repository, fixed commit and workspace copy. Fields retained for the whole
run include the histories and totals used by stall and budget checks. Updates append to
\demoref{messages} and \demoref{observations}, and add to \demoref{model\_calls} and
\demoref{usage}. The current fields, \demoref{candidate\_patch} and \demoref{status}, hold the
latest patch and execution status.

Our \demoref{add\_usage} reducer keeps four separate token totals. Cached input costs less than
fresh input, so a combined total could hide an increase in one alongside a decrease in the
other. In both agents, however, the code that reads model replies fills only the input and
output counters. The two cache counters are zero in both recorded runs of the planning agent.

The planning agent (\cref{fig:agentstate}, right) adds five fields. The plan node writes
\demoref{plan}, the submit node writes \demoref{checks}, and the validator writes
\demoref{validation}. Each holds the latest value, so these three fields use the current
lifetime. The remaining two fields use handoff and window lifetimes.

\bi

\item \textbf{Handoff.} When the tools node detects a stall, it writes the reason to
\demoref{failed\_step}. The routing function reads this field and selects the plan node. That node
reads the reason, revises the plan and clears \demoref{failed\_step} to \demoref{None}. If it left
the field set, the next pass through \demoref{tools} would return to the plan node again.

\item \textbf{Window.} The \demoref{observations} list keeps growing and is never cleared.
Immediately after a plan revision, its last three entries are still the repeated results that
caused the revision. To avoid detecting the same stall again, the plan node stores the current
observation count in \demoref{replanned\_at}. The stall check then reads only
\demoref{observations[replanned\_at:]}. A nonzero value also records that the one permitted
revision has been used. If the run stalls again, it ends.

\ei

Each field passes information from a step that writes it to a later step that reads it
(\cref{tab:state-flow}).

The following code shows the difference between model context and runtime state
(\cref{sec:state-three}). The controller sends the conversation to the model. Before making
that call, the runtime compares the call counter with the configured budget.
\textbf{The runtime checks the budget before the call; the controller's context does not
contain it.} The planning agent's other prompts also omit the budget.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize]
# controller: the model receives the conversation
reply = self._call(model, state["messages"],
                   role="controller")

# admission: run before every model call
if state["model_calls"] >= self.config.budget:
    return {"status": TerminalStatus.BUDGET_EXHAUSTED}
\end{lstlisting}
\end{minipage}

We define a state graph in the following order.

\be

\item Name the nodes and the routing decisions between them.

\item List the values that nodes and routing functions must read. These values define the schema.
Omit fields that no computation reads.

\item For each field, identify which node writes it and when the value becomes outdated.
Choose its lifetime using \cref{sec:state-lifetimes}.

\item Choose a merge rule that supports that lifetime: no custom reducer for identity, append
or accumulate for run, and replacement for current, handoff and window. For an attempt field,
make sure the rule allows the value to be cleared.

\item Write the initial state so that every key has a value before the first node runs.

\item Have each node return only the fields it is responsible for updating. When adding a
field, also add the node code that supplies its value.

\ee

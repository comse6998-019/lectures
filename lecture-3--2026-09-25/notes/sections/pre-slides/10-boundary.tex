\section{Scheduling, tools, and execution authority}
\label{sec:boundary}

\subsection{Scheduling: when an update becomes visible}
\label{sec:boundary-scheduling}

The routing function chooses the next location. The scheduler determines when the computation at
that location runs, which version of the record it reads, and when later computations can read
its update.

\begin{definition}[Superstep]
\label{def:superstep}
``Pregel computations consist of a sequence of iterations, called supersteps.'' By design, the model
``doesn't expose any mechanism for detecting order of execution within a superstep, and all
communication is from superstep $S$ to superstep $S + 1$''~\citep[\S1]{malewicz2010pregel}.
\end{definition}

A runtime using this model divides each superstep into three phases. i) During \emph{planning},
it selects computations whose inputs were written in the previous superstep. ii) During
\emph{execution}, it runs those computations. Their writes remain invisible to other computations
in the same phase. iii) During \emph{update}, it applies the writes using the reducers of
\cref{sec:state-reducers}. The next superstep's planning phase uses the updated record. In the
notation of \cref{sec:state-transition}, execution computes $u_t$, and the update phase computes
$\mathrm{merge}(s_t, u_t)$.

The runtime therefore applies a node's writes after the node returns and before planning the
next node. \textbf{A later node never reads a partly applied update.} Nodes in the same superstep
cannot see one another's writes. The runtime combines those writes in the update phase. If two
nodes write the same field, that field needs a reducer to combine their values. Without one, the
runtime must reject the competing writes.

This guarantee applies only to the record. A tool can change a file during execution, before the
superstep ends. If the node then fails, the file remains changed, but the record receives no
update describing that change. \textbf{The superstep rules determine when record updates become
visible. They do not control changes to files or other external resources.} The checks around
tool execution must control those effects.

\subsection{The tool contract}
\label{sec:boundary-contract}

The model receives a tool's name, description, and argument schema. The runtime holds the code
that implements the tool. It enforces restrictions on what the tool may do and handles invalid
arguments. The description alone cannot enforce these restrictions.

\begin{definition}[Tool contract]
\label{def:tool-contract}
A \emph{tool contract} specifies five parts of a tool: i) its name and purpose, ii) the types of
its arguments and the restrictions on their values, iii) the type of a successful result and how
errors are represented, iv) its side-effect class, which describes the kinds of external changes
it can make, and v) restrictions on execution, such as the directories it may access. The
definition supplied to the model covers the first two parts. The tool's implementation and the
dispatcher determine the other three. The model cannot establish them from the description.
\end{definition}

A method specification states what the caller and the implementer must each ensure
(\citealp[Specification structure]{mit6031-specs}).

\begin{definition}[Precondition]
\label{def:precondition}
``The precondition is an obligation on the client (the caller of the method). It is a condition over
the state in which the method is invoked.''
\end{definition}

\begin{definition}[Postcondition]
\label{def:postcondition}
``The postcondition is an obligation on the implementer of the method.'' ``In general, the
postcondition is a condition on the state of the program after the method is invoked, assuming the
precondition was true before.''
\end{definition}

For a tool, the precondition states which argument types and values are allowed, including any
restrictions on execution. For example, a path may have to resolve inside the workspace. The
postcondition states what the tool promises about its result, errors, and side effects. These
promises apply when the precondition holds.

A method specification may make no promises if the caller violates a precondition. An agent's
tool contract needs stricter rules for this case, because the model can supply invalid arguments
during normal operation. The contract must state which violations the runtime detects and how
it reports a refusal. It must also require that a refused request has no side effects.
\textbf{A tool contract must define how the runtime handles violated preconditions.}

Our three tools illustrate this contract. \demoref{read\_file} takes a path and an optional line
range, then returns text. \demoref{search} takes a regular expression and an optional glob, then
returns matching lines with their locations. \demoref{edit} replaces one exact occurrence of a
string in a file. Only \demoref{edit} writes. All three take the workspace root as their first
parameter. Before opening a file, \demoref{read\_file} and \demoref{edit} resolve its path using
that root. \demoref{search} matches its glob against the root without resolving paths
(\cref{sec:boundary-demo}).

The dispatcher uses the function signature to decide which arguments to accept. This also
determines who can supply configuration values. Our tools read the run's configuration from the
module; they have no configuration parameter. The dispatcher binds the model's arguments to the
parameters in the signature. As a result, \textbf{a parameter the dispatcher has not already
supplied can receive a value from the model}. Adding a \demoref{config} parameter would let the
model set it. The dispatcher itself supplies the workspace-root parameter, which is absent from
the model's schema. If the model names that parameter anyway, binding fails because the
dispatcher has already supplied its value.

\subsection{The dispatch cycle}
\label{sec:boundary-dispatch}

The dispatch cycle processes a tool request in five operations. Each operation can end the cycle.
\Cref{fig:dispatch-cycle} follows one request through them.

\begin{figure}[htbp]
  \centering
  \begin{adjustbox}{width=\linewidth}\input{figures/lecture-3/dispatch-cycle.tikz}\end{adjustbox}
  \caption{The stages of processing one tool request. Ellipses show the incoming request and the records
  that receive the observation; grey boxes show runtime work. Solid arrows follow successful
  checks. Dashed arrows show refusals, which also produce observations. A policy check may run
  inside the tool, as in our implementation, provided it runs before the operation it protects.}
  \label{fig:dispatch-cycle}
\end{figure}

\bi

\item \textbf{Resolve the name.} The dispatcher looks up the requested name in its registry,
which it builds from the tool enumeration. If the name is absent, it refuses the request and
lists the available tools in its response. Supplying a tool definition to the model cannot make
an unregistered tool run.

\item \textbf{Bind the arguments.} Before calling the function, the dispatcher matches the model's
arguments to its signature. If an argument name is wrong, it reports a readable refusal without
letting a \demoref{TypeError} arise inside the tool. Binding checks argument names and arity, the
number of arguments. It does not check their types. The dispatcher separately converts values
when the required conversion is unambiguous. For example, it can convert a string supplied where
an integer was required, avoiding an extra model call to correct the request.

\item \textbf{Check the policy.} Before opening a file, the tool resolves its path. If the resolved
path lies outside the workspace root, it refuses the request. This check is the first operation
in \demoref{read\_file} and \demoref{edit}. The dispatcher converts any exception from the check
into a refusal.

\item \textbf{Perform the permitted operation.} The function runs with the bound arguments and the
dispatcher's workspace root.

\item \textbf{Observe.} The dispatcher creates an \demoref{Observation} for both success and
failure. It contains the tool, the arguments, an \demoref{ok} flag, and a string result. The
dispatcher also writes a \demoref{tool\_result} event in either case.

\ei

A refusal returns an observation to the model, allowing the reactive loop to continue. An
exception that escapes this handling ends the run. If \demoref{edit} refuses an ambiguous target,
the model can use the observation to retry with more context. Allowing an exception to escape
would end the run at that first imprecise edit. Exceptions that end the run are reserved for
unrecoverable failures, such as an unwritable trace.

If a model response contains several tool calls, the tools node dispatches them one at a time
within one superstep. It returns an observation for each call, including failed calls. If it
omits a response to any call, the next model message is malformed.

Step 4 falls between the model response and the tool request. It is a routing event with decision
\demoref{tools} and \demoref{by="model"}, because the reply contained a tool call
(\cref{sec:control-routing}). It records the selected control location. It does not describe tool
execution.

The model response tells us what the model requested. It cannot establish that a file operation
occurred. Even if the model writes both a request and a plausible result in a transcript, neither
shows that the tool ran. In this example, the runtime's \demoref{tool\_result} event has
\demoref{ok=true}, establishing that the function ran and returned. We must check this flag,
because a result event can also report a refusal before the function is called. The successful
event records the length of the returned text. It cannot establish the text's contents.

\subsection{Execution authority}
\label{sec:boundary-authority}

The model proposes actions; the runtime executes or refuses them. We can identify the component
responsible for each step as the request is processed. We must also show that the required checks
run on \emph{every} route by which an action can execute.

\begin{definition}[Complete mediation]
\label{def:complete-mediation}
``To attempt to secure this resource, server needs to check all accesses to the resource.
`Complete mediation.' '' ``Server will put a `guard' in place to mediate every request for this
particular resource. Only way to access the resource is to use the guard.''~\citep[\S5]{mit6033-lec20}
\end{definition}

For an agent, a resource is anything a tool can affect, including files, processes, or the network.
The request is a tool call. The guard consists of the checks that run before the tool affects the
resource. Complete mediation means that every route to the resource passes through those checks.
Testing one route cannot establish what happens on a route that bypasses the checks. We therefore
need to list every route to each protected operation. It is easy to overlook a route, such as a
new tool or an argument that identifies a file without being named a path. Complete mediation
ensures that the runtime checks the policy on every route. Whether the policy itself is correct
is a separate question.

The term ``control'' can refer to two different questions.

\bi

\item \textbf{Who decides, and when?} We fix some choices when we write the program. The program
computes others while it runs. The time of a decision does not tell us who controls it: a routing
function and a limit check both run during execution, and both apply rules the programmer wrote.

\item \textbf{Who proposes, and who executes?} A requested action, a claimed result, or a
declaration that the work is finished takes effect only when the runtime processes it. A model's
statement that it ran the tests does not establish that tests executed.

\ei

  \centering

Before comparing the workspace root and the requested path, \demoref{workspace.resolve} fully
resolves both. It follows symlinks and resolves \demoref{..} segments, so neither can hide a
destination outside the root. Checking only whether one string starts with another would fail:
\demoref{/tmp/ws} is also a prefix of the unrelated directory \demoref{/tmp/ws-evil}. Joining an
absolute path to the root yields the absolute path itself. The check refuses it if its resolved
destination lies outside the root.

\subsection{The demo: scheduling and request refusal}
\label{sec:boundary-demo}

Our planning agent runs on LangGraph's runtime. It organizes execution ``into multiple steps, following
the Pregel Algorithm/Bulk Synchronous Parallel model''. During execution, ``channel updates are invisible to actors until the next step''~\citep{langgraph-pregel}.
Our graph has no parallel branches, so each superstep runs one node. In run \demoref{bc284c6b},
steps 3 and 4 belong to the controller's superstep: first the model call, then the routing event.
The routing function reads the record after the controller's reply has been merged. Steps 5 and
6 belong to the next superstep. The tools node reads the reply and dispatches its call, and the
dispatcher writes both trace events during execution. The runtime adds the observation to
\demoref{observations} in the update phase, after the node returns.

No recorded run contains a refused request. For this demonstration, we send requests directly to
the dispatcher, outside a graph. We use a fresh workspace for the worked alert and report the
dispatcher's responses. The first request calls \demoref{read\_file} on
\demoref{testcode/BenchmarkTest00283.py}. The dispatcher permits it and returns the same 1,665
characters as step 6 of the recorded run. The second request changes only the argument.

\bi

\item \textbf{The request.} \demoref{\{"name": "read\_file", "args": \{"path":
"../../etc/passwd"\}\}}, which no model produced.

\item \textbf{The check that refuses it.} The first operation in \demoref{read\_file} is
\demoref{workspace.resolve}. It raises \demoref{PathEscapeException}, which the dispatcher catches.

\item \textbf{The record.} The dispatcher returns an observation with \demoref{ok=false} and the result
\demoref{refused: \textquotesingle../../etc/passwd\textquotesingle{} resolves outside the workspace root}.
It also writes a \demoref{tool\_result} event with the same reason.

\item \textbf{Evidence that no file was opened.} The trace contains a \demoref{tool\_request} event
and a failed \demoref{tool\_result} event with a reason and no character count. These events show
that the runtime refused the request. To establish that no file was opened, we must also read the
code: the check runs before the first file operation. The trace records no file operations, so
it cannot establish this on its own.

\ei

The two requests use the same tool and dispatcher. Their arguments determine whether the runtime
permits or refuses them. This example identifies the component that enforces the rule described in
\cref{sec:boundary-authority}.

The same exercise shows a route that bypasses the check. The dispatcher permits a
\demoref{search} whose glob reaches outside the workspace. With the glob
\demoref{../*-withheld/testcode/*.py}, it returns lines from the withheld benchmark cases stored
in a sibling directory. With enough \demoref{../} segments, it returns the matching line
of \demoref{/etc/passwd}. Both results have \demoref{ok=true}.
\textbf{The path check guards \demoref{read\_file} and \demoref{edit}; it does not guard
\demoref{search}, whose glob never passes through \demoref{workspace.resolve}.} The check covers
every way these tools can write outside the workspace, because \demoref{edit} is the only tool
that writes. It leaves a way to read outside the workspace unchecked. To close this route,
\demoref{search} must pass every matching file through \demoref{workspace.resolve} before reading it.

\subsection{Reading}

Read \S1 and \S2 of \citet{malewicz2010pregel} for supersteps and the rule that communication
crosses superstep boundaries in one direction only. Read the section ``Specification
structure'' of \citet{mit6031-specs} for preconditions and postconditions, and \S5 and \S6 of
\citet{mit6033-lec20} for the guard model and ways to bypass complete mediation.

When writing HW1, consult \citet{langgraph-pregel} for the planning, execution and update phases
in our runtime. Use \citet{anthropic-tooluse} for the exact format of requests and results that a
provider sends and expects. See \demoref{dispatch.py} and \demoref{workspace.py} for the checks
that run between a request and its result.

\paragraph{Looking ahead.} In the execution model described here, a routing function selects a
node and the scheduler runs it in the next superstep. The next section keeps the same machine
and changes this scheduling mechanism: a computation emits an event, which the runtime dispatches
to a registered handler. We then examine which component invokes the handler and when. The tool
contract and dispatcher remain the same. We will need evidence that each transition occurs once
under the new scheduling mechanism.

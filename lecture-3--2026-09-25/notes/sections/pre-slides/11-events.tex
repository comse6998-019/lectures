\section{An event-triggered implementation}
\label{sec:events}

\subsection{Events, handlers and inversion of control}
\label{sec:events-ioc}

A graph and an event loop can run the same machine. They differ in how they call the application
code. In the graph, a routing function selects the next node, and the scheduler runs it in the next
superstep (\cref{sec:boundary-scheduling}). In an event loop, a computation emits an event, and the
runtime calls the code registered to handle that event. The following four definitions describe
this arrangement. All four come from the same source~\citep[Event Handling; Understanding the
Event Loop]{cornell-cs2110-lec25}.

\begin{definition}[Event]
\label{def:event}
``An event is any occurrence that could necessitate a change in the program's state.''
\end{definition}

\begin{definition}[Handler]
\label{def:handler}
Handlers are ``pieces of code that understand how to respond to a particular event''; for events to
reach them, they ``must register with the event loop.''
\end{definition}

\begin{definition}[Event loop]
\label{def:event-loop}
``An event loop is a piece of code that repeatedly checks whether a new event has occurred and
dispatches any detected events to code that can handle them.''
\end{definition}

\begin{definition}[Inversion of control]
\label{def:inversion-of-control}
``Inversion of control is used to describe the paradigm where we write custom subroutines but allow
an external entity, such as a framework, to control when these subroutines are executed.''
\end{definition}

For an agent, an event can represent something that happened, such as \emph{the plan is ready} or
\emph{the checks failed}. It can also represent a request, such as \emph{run these tools}. The
program represents both kinds of event as values. A tool request event asks a handler to do work.
The request alone provides no evidence that the handler ran. The same distinction applies to a
model's tool request in \cref{sec:boundary-artifacts}: a request to read a file provides no evidence
that the read occurred.

Inversion of control separates two responsibilities. Application code defines how each handler
responds to its event: what work it does, which fields of the record it writes, and which event it
emits when it finishes. The framework determines which handler runs, when it runs, and the order
in which it processes pending events. \textbf{Application code defines the response to an event;
the framework controls when the handler runs.} The graph implementation divides these
responsibilities in a similar way: we write node bodies and routing functions, and the scheduler
runs them. The two implementations choose the next computation in different places. A graph uses
a routing function on an edge. An event handler chooses the type of event to emit, and the
registrations associate that type with a handler.

The registrations determine which event types have handlers. A loop that does not check its
registrations can remove an event from the queue even though no handler accepts that event's
type. No handler then runs, although no component has decided to stop. The framework's
implementation determines whether it reports this as an error. We classify this case as a defect.

\subsection{An event-triggered version of the machine}
\label{sec:events-machine}

Changing the implementation changes when the runtime takes a transition while preserving the
set of transitions. A state-machine diagram alone does not specify when a reaction occurs. In an
event-triggered model, a reaction occurs when an input is present. In a time-triggered model, it
occurs on the tick of an external clock~\citep[slides~23--25]{seshia2015discrete}. Either model can
use the locations, guards and set actions of the planning agent's machine
(\cref{fig:efsm-planner}). Our graph implementation uses no clock: each superstep begins when the
preceding one finishes. The event implementation reacts when an event is present, so it is
event-triggered under this definition.

The choice of trigger can still make a transition unreachable. A guard requiring every triggering
input to be \emph{absent} cannot fire when a reaction requires a triggering input to be present.
Each transition of the planning agent becomes enabled when the preceding computation completes,
so it can wait for an event reporting that completion. A transition such as \emph{no reply arrived
within thirty seconds} needs a timer to emit an event when the thirty seconds end. Without that
timer, the runtime never takes the transition even though it appears in the diagram.

The event implementation needs a larger configuration to describe its execution. In the graph
implementation, a configuration is $(q, v)$: a control location $q$ and a valuation $v$, which
assigns a current value to each variable (\cref{def:configuration}). In the event implementation,
the configuration is a triple
\[
  (E,\ \mathcal{H},\ v),
\]
where $E$ is the sequence of pending events, $\mathcal{H}$ is the set of running handlers, and $v$
is the record. The runtime maintains the event queue $E$ and the running handlers $\mathcal{H}$
separately from the record, which stores the steps' data. In a serial implementation, at most one
event is pending or being handled. During active execution, either one event is pending and no
handler runs, or one handler runs and no event is pending. We can then recover the location $q$
by identifying the handler registered for the pending event or the handler already running. An
implementation that permits two handlers to run at once can reach a configuration with no single
location $q$. The machine in \cref{fig:efsm-planner} cannot describe such a configuration. Our
demo's validation step provides an example (\cref{sec:events-demo}).

Four rules preserve the machine's behaviour when an event loop implements it.

\bi

\item \textbf{Apply once, then enable.} Merge a handler's contribution into the record exactly
once. Complete this update before making its emitted event available for dispatch. The graph's
superstep model provides this ordering (\cref{def:superstep}). An event loop provides it only if
the handler writes before it emits and the runtime delivers the event only once. If a handler
emits first, the next handler can read the record before the update appears. If the runtime
delivers an event twice, the handler appends the same observations twice.

\item \textbf{Distinguish idle from success.} An empty queue with no running handler means that
nothing is scheduled. This alone does not explain how the run ended or whether it ended
intentionally. Establishing termination requires a terminal event carrying a status, just as it
requires a terminal record in the trace (\cref{sec:control-termination}).

\item \textbf{Stop dispatch at termination.} After dispatching the terminal event, the runtime
must start no further handler, even if an event remains pending. In a serial implementation, no
event can be pending at that point. An implementation with concurrent handlers must discard or
refuse the remaining events.

\item \textbf{Separate triggering events from log events.} A triggering event causes the
dispatcher to run a handler. A log event records something that happened and starts no
computation. For example, an event requesting tools starts the tools handler. A trace record of
the same request documents that the handler was called; it starts no further computation.

\ei

The third and fourth rules both apply when a run ends. The terminal event ends dispatch, and the
terminal record in the trace stores the status. If the process fails before writing that record,
dispatch can end without a recorded status. The interpretations in \cref{tab:control-outcomes}
still apply.

\subsection{Two frameworks}
\label{sec:events-frameworks}

Two frameworks provide event dispatch through different APIs.

\bi

\item \textbf{LlamaIndex Workflows.} The framework selects a step by event type. A step is a method decorated with
\texttt{@step}, and ``A step receives an event, does some work, and returns another event. That
returned event triggers the next step whose type annotation accepts it''~\citep{llamaindex-workflows}.
Users define event types as Pydantic classes. The framework also supplies two event types:
\texttt{StartEvent}, whose fields are the keyword arguments passed to \texttt{run()}, and
\texttt{StopEvent}, whose return ends the workflow with the value passed as its \texttt{result}.
Each step's signature declares the event types it accepts and emits. Before a run, the framework
checks the event graph described by these signatures. Among other conditions, it checks that the
graph contains a start event and a stop event and that every emitted event has a step that accepts
it. The workflow's \texttt{Context} includes a store for state that belongs to the run. Steps
read and write this state through \texttt{ctx.store}. They use \texttt{edit\_state()} when an
update must finish before another step can update the same store~\citep{llamaindex-workflows-state}.
Our demo uses this framework (\cref{sec:events-demo}).

\item \textbf{CrewAI Flows.} The framework selects methods using completion events and route
labels. A method decorated with \texttt{@start()} is an entry point. A method decorated with \texttt{@listen(m)} runs when
method \texttt{m} completes and receives its output. A method decorated with \texttt{@router(m)}
runs after \texttt{m} and returns a string label. Methods decorated with \texttt{@listen("label")}
run when the router returns that label. The operators \texttt{or\_} and \texttt{and\_} combine
triggers. With \texttt{or\_}, the listener runs when any of the specified methods produces output;
with \texttt{and\_}, it waits for all of them. The flow's \texttt{state} attribute holds shared
state as a dictionary or a Pydantic model. There is
no stop event: ``the final output is determined by the last method that completes''~\citep{crewai-flows}.
To translate our implementation to CrewAI, we would turn each event type into a router label.
Our code would also have to write the outcome $\sigma$ to \texttt{state}, because the end of the
flow does not carry that outcome.

\ei

The frameworks therefore distinguish idle from success in different ways. LlamaIndex provides an
explicit terminal event. Its checks before execution inspect the event graph declared by step
signatures for start and stop events and missing connections. Passing these checks does not
establish that a particular run will reach \texttt{StopEvent}. CrewAI defines no terminal event.
Our reading of its documentation is that a flow ends when no method remains to run, corresponding
to an empty queue. The application must therefore record the outcome before the last method
completes.

Using either framework leaves a further question: does the event implementation preserve the
machine's behaviour? To compare it with the graph implementation, we need a controlled design.
In this design, we compare the implementations after each computation finishes and its
contribution has been applied to the record. These points let us compare the effects of completed
computations without depending on a handler's internal steps or their wall-clock timing. We
script the model's replies and control the tool results so that both implementations receive the
same inputs in the same order. A faithful translation preserves four properties at each point:
i) the observations appended to the record, ii) the effects on the workspace, iii) the results of
the acceptance checks, and iv) the terminal status and its meaning. This comparison is designed
to isolate the scheduling mechanism: a graph superstep or an event dispatch.

If the implementations agree under these scripted inputs, we can conclude that they follow the
same transition rules for those replies. This does not establish that they behave alike with a
live model. The model's replies depend on the messages each implementation constructs. Changing
how a handler formats a message changes the model's input even when the transition rules stay the
same. This comparison also excludes concurrent execution.

\subsection{The demo: the planning agent as a LlamaIndex workflow}
\label{sec:events-demo}

The event implementation, \demoref{cyberbird/event\_driven}, runs the planning agent's machine as a
LlamaIndex workflow. It preserves the machine's locations, guards and limits. Each alert has a
budget of forty model calls, checked before each call. Three identical results count as a stall,
and the agent may revise its plan once. The workflow stores the run's data in its context.
\demoref{RunState} holds bookkeeping for the whole run. Each alert has an \demoref{AlertState}
that holds its plan, messages, observations, calls and usage. Two steps are still stubs:
\demoref{submit} runs no mechanical checks, and each validator accepts after a fixed delay
without calling a model. No run of this agent has been recorded.

The six rows below the horizontal rule in \cref{tab:events-steps} correspond to the machine's
locations. Step signatures define the connections between steps. The framework sends each event
to the step whose signature accepts its type, so each step can run without naming the next step.
The graph's routing functions evaluated the guards. Here, the steps evaluate those guards to
choose which event to return.

\bi

\item \textbf{Admission.} Before calling the model, \demoref{plan} and \demoref{controller} reserve
one call from the alert's budget. If the budget is exhausted, the step returns \texttt{AlertDone}
with status \demoref{budget\_exhausted}. It makes no model call in that case.

\item \textbf{Acting.} The controller returns \texttt{ToolsRequested} when the model's reply
contains tool calls, and \texttt{Submitted} when it contains none.

\item \textbf{Revising.} While the agent has not stalled, \demoref{tools} returns
\texttt{Observed}. At the first stall, it returns \texttt{Stalled}, which starts the plan step.
That step writes a new plan and updates \demoref{replanned\_at}. These updates provide the
handoff and the start of the observation window described in \cref{sec:state-lifetimes}. At a
second stall, the tools step returns \texttt{AlertDone} with status \demoref{no\_progress}.

\ei

The event implementation also adds three behaviours to the graph implementation. First, one run
can handle many alerts. \demoref{scan} runs Bandit once and emits one \texttt{AlertFound} for each
alert. The \demoref{gate} step queues the alerts it receives and starts one at a time. It starts
the next alert only after receiving \texttt{AlertDone} for the current alert. Every event about
an alert carries an \demoref{alert\_id} that links the event to that alert's entry in the store.

Second, validators run concurrently, and a judge collects their results. \demoref{submit} sends
one \texttt{ValidateRequested} for each aspect of validation: correctness, behaviour and scope.
It sends these events through \demoref{ctx.send\_event}, because a step can return only one
event. The validate step has up to three workers, allowing the three validators to run at the
same time. This gives the configuration described in \cref{sec:events-machine}, with several
running handlers and no single location. \demoref{judge} stores each \texttt{Verdict} until all
$V$ verdicts have arrived, in any order. It accepts the alert only if every validator accepted.
The judge collects verdicts without grouping them by alert. This is safe only because the gate
admits one alert at a time. \textbf{The gate processes alerts one at a time and allows validators
for the current alert to run concurrently.}

Third, the implementation distinguishes the end of an alert from the end of the whole run. An
alert ends with an \texttt{AlertDone} carrying one of
four statuses: \demoref{accepted}, \demoref{rejected}, \demoref{no\_progress} or
\demoref{budget\_exhausted}. The gate receives this event and records the status. When it has a
result for every alert found by the scan, the gate returns a \texttt{StopEvent} carrying all the
results and ends the run. If the scan finds no alerts, it ends the run immediately with an empty
result.

The implementation handles the four rules of \cref{sec:events-machine} as follows.

\bi

\item \textbf{Apply once, then enable.} Every write uses \demoref{ctx.store.edit\_state()}, which
locks the store. Each step writes its data before emitting the event that allows another step to
read them. The budget check and reservation use the same lock. Two steps requesting admission
at the same time therefore cannot both reserve the last available call.

\item \textbf{Distinguish idle from success.} A \texttt{StopEvent} explicitly ends the run. The
gate emits it after collecting all alert results; the scan emits it if it finds no alerts. Before
the first run, the framework also checks that every emitted event has a step that accepts it.
For this check, \demoref{submit} lists \texttt{ValidateRequested} in its return annotation even
though it sends those events through \demoref{ctx.send\_event}.

\item \textbf{Stop dispatch at termination.} The gate emits \texttt{StopEvent} only when the
number of results equals the number of alerts. Every alert has therefore finished when the gate
ends the run.

\item \textbf{Separate triggering events from log events.} This agent's events trigger steps.
The agent currently writes no trace of their execution. Our graph agents also write a trace
(\cref{sec:control-termination}); the event implementation still needs this feature.

\ei

Loop, for events, handlers, the event loop and inversion of control. Read \citet{seshia2015discrete},
slides 23--25, for event-triggered and time-triggered reactions.

the final output, conditional logic and the router.

\paragraph{Looking ahead.} In an event loop, the runtime calls a registered handler when its event
arrives. That handler can emit any number of events. Deciding whether this work is permitted and
measuring its cost require further mechanisms. The next section introduces admission, which
decides whether a model or tool call may start, and accounting, which records its cost after
execution. It also considers how to compare the costs of implementations under controlled
conditions like those used here to compare behaviour.

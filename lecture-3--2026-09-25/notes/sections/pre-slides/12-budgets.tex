\section{Budgets and controlled measurement}
\label{sec:budgets}

\subsection{Admission and accounting}
\label{sec:budgets-admission}

To limit spending, a runtime needs two mechanisms that act at different times. Before a model or tool
call, it must decide whether the call may start. After the call runs, it must record the cost.
The first mechanism uses information available before the call. The second uses the usage reported
afterwards.

\begin{definition}[Admission]
\label{def:admission}
Admission decides whether a unit of work may start. It checks how much of the run's limit is
already committed, then permits or refuses the work. Refused work never runs and incurs no charge.
\end{definition}

\begin{definition}[Accounting]
\label{def:accounting}
Accounting records the cost of a unit of work after it runs. It adds the charge to a running
total, measured in the same units as the limit. Admission reads this total.
\end{definition}

The two mechanisms work together to enforce the limit. If accounting leaves a call out of the
total, admission can allow more work than the limit permits. If admission never checks the total,
accounting can record an overrun only after it happens. \textbf{Accounting maintains the usage
total; admission uses it to enforce the limit.}

Accounting reads the charge reported with each reply. Admission must decide before the reply
exists, when it knows the input to be sent but has not seen the output. A call-count limit is
therefore easier to enforce than a token limit. Each call counts as one, so admission knows its
cost in advance. The token cost becomes known only after the call runs.

The graph implementation of our planning agent uses call-count admission. It checks a budget of
forty calls before each model call and records the call's input and output tokens. The token
admission and reservation mechanism developed below is a proposed design. Our code does not
implement it.

Call counts provide only a rough measure of token usage. In our two recorded runs, individual
calls have inputs ranging from 571 to 13{,}550 tokens. Each controller call resends the
conversation, which grows during the run. A budget of forty calls limits the number of replies.
The token cost of those forty calls still depends on the largest possible call.

\subsection{A budget invariant}
\label{sec:budgets-invariant}

Admission and accounting must use a clearly defined budget unit. The choice of unit determines
which cost the budget limits. We consider three choices.

\bi

\item \textbf{Output tokens.} Count only tokens generated by the model. A per-call output limit
sets a bound on each call's cost before it starts, which simplifies admission. This budget leaves
out input tokens, whose count grows as calls resend the conversation.

\item \textbf{All processed tokens.} Count input and output tokens together to track the provider's
work. Admission then needs a bound on both the input and the output of each call.

\item \textbf{Money.} Multiply token counts by their prices. Different kinds of tokens, such as
cache reads and fresh input, can have different prices. Accounting must keep these counts separate
until it calculates the charge. A change in prices changes how much work the budget permits.

\ei

\noindent The following argument applies to all three choices. The chosen unit determines how we
calculate a call's charge $\gamma$.

We state the budget rule as an invariant using three quantities. $B$ is the budget. $S$ is
\emph{settled spend}: the sum of recorded charges for completed calls. $R$ is the total still
reserved for calls that have been admitted but whose charges have not yet been recorded. These
are the \emph{outstanding reservations}. The invariant is
\[
  S + R \;\leq\; B .
\]
A \emph{reservation} $\rho$ sets aside part of the budget for a call before it starts. This
amount must be a justified upper bound on the call's cost. After the call completes,
\emph{settlement} replaces its reservation with the recorded charge $\gamma$.

We want to bound the charges themselves: the total charge for every call the run has started,
including unfinished calls, must never exceed $B$. As with the call counter in
\cref{sec:state-invariants}, the runtime can compare only the values it has recorded. We need a
further requirement to connect the invariant over these recorded values to the charges:
\[
  \forall i.\; \gamma_i \leq \rho_i ,
\]
where $i$ ranges over admitted calls, $\rho_i$ is the reservation for call $i$, and $\gamma_i$ is
its charge on completion. Admission must choose $\rho$ so that this requirement holds. The
requirement is not a state predicate that the runtime can check: for an outstanding call, the
runtime does not yet know the final charge $\gamma_i$. The input and output bounds below justify
the requirement. If it holds, $S + R$ bounds the total charge of all calls started. Keeping
$S + R$ within $B$ then keeps those charges within the budget. We use the invariant method
(\cref{def:invariant}) to show that the inequality holds initially and remains true after every
transition.

\bi

\item \textbf{Initially.} The run has admitted no calls and recorded no charges, so $S = 0$ and
$R = 0$. The invariant therefore holds for any $B \geq 0$.

\item \textbf{Admit.} Admission checks whether the new reservation fits: $S + R + \rho \leq B$.
If it does, admission sets $R$ to $R + \rho$, reserving $\rho$ for the call. This guard ensures
that the invariant still holds. If the reservation does not fit, admission refuses the call and
leaves the record unchanged.

\item \textbf{Settle.} The call completes with charge $\gamma$. Settlement adds this charge to
the recorded total, setting $S$ to $S + \gamma$. It also removes the reservation, setting $R$ to
$R - \rho$. Their sum changes by $\gamma - \rho$. Since $\gamma \leq \rho$, the sum cannot grow,
and $S + R \leq B$ still holds. The unused amount $\rho - \gamma$ becomes available for later
calls.

\item \textbf{Release.} An admitted call may never be issued, for example if the run ends first.
The runtime then removes the reservation by reducing $R$ by $\rho$. The call incurred no charge,
so the invariant continues to hold.

\item \textbf{Every other transition.} Leave $S$ and $R$ unchanged. No transition decreases $S$:
settled spend lasts for the whole run, as defined in \cref{sec:state-lifetimes}. Resetting $S$ to
zero would make the budget available again even though the run had already incurred those charges.

\ei

Concurrent calls require one further condition: checking the guard and recording the reservation
must form a single step. Suppose two model calls are admitted in the same superstep
(\cref{sec:boundary-scheduling}). Both could check $S + R + \rho \leq B$ before either adds its
reservation to $R$. Each check could then pass even though the combined cost exceeds $B$.

The proof depends on showing that $\gamma \leq \rho$. If the budget counts all processed tokens,
$\rho$ must cover both input and output. We need to justify a bound for each.

\bi

\item \textbf{Input.} Establish an upper bound on the call's input tokens. Before sending the
call, the runtime can use the provider's counting endpoint to obtain an estimate: ``The token
count is an estimate. In some cases, the actual number of input tokens used when creating a message
might differ by a small amount''~\citep{anthropic-token-counting}. Comparing past estimates with
recorded charges can help choose a margin to add to the estimate. A strict guarantee requires a
justified upper bound on the estimation error. Another option is to use a limit that the request
cannot exceed, such as the model's context window.

\item \textbf{Output.} Use an upper bound that the provider enforces. The request specifies a
per-call output limit, and the provider stops generation when that limit is
reached~\citep{anthropic-stop-reasons}. The bound holds even if the model would otherwise have
generated more content.

\ei

An estimate alone cannot justify the invariant. If admission bases $\rho$ on an estimate and the
call costs more, settlement increases the sum by $\gamma - \rho > 0$. The record contains no
flag showing which step caused $S + R$ to exceed $B$. \textbf{The guarantee from reservations
requires an upper bound on each call's charge.} Estimates help forecast spending. To guarantee
that spending stays within $B$, we need the bounds described above.

The runtime must also handle unused reservations and uncertain charges. It must release unused
reservations so that useful work can continue. This is a liveness requirement: an unused
reservation keeps $R$ high and can cause admission to refuse work that would otherwise fit.
Keeping that reservation does not violate the spending invariant. An uncertain charge needs a
different response. If a timeout or crash prevents the runtime from receiving a reply, the
provider may still have charged for the call. Releasing the reservation could leave that charge
out of the record. The runtime must keep the reservation until it checks the charge against the
provider's usage records. Only then can it settle the call or release the reservation.

\subsection{Exhaustion and truncation}
\label{sec:budgets-limits}

A budget and a per-call limit stop work at different points. The budget prevents a new call from
starting. The per-call limit stops generation after a call has started. A run can reach either
limit, and the two cases have different consequences.

\bi

\item \textbf{Exhaustion.} Admission refuses the next call, so it never starts. The run ends with
a declared status, and a terminal event in the trace records the reason
(\cref{tab:control-outcomes}). Calls already running continue until they finish, when accounting
settles their charges.

\item \textbf{Truncation.} A call reaches its output limit, so the provider stops generation. The
provider returns a successful response containing the content generated so far and reports why
generation stopped.

\ei

Truncation matters especially when the model requests a tool. The provider's documentation
describes the problem:
``If Claude's response is cut off because it hit the \texttt{max\_tokens} limit,
and the truncated response contains an incomplete tool use block, you'll need to retry the request
with a higher \texttt{max\_tokens} value to get the full tool use''~\citep{anthropic-stop-reasons}.
A truncated request can still name a known tool and supply arguments that match its signature.
For example, an edit request can have valid argument names but incomplete replacement text. The
dispatch checks in \cref{sec:boundary-dispatch} test the tool name, number of arguments and policy.
They do not check whether the requested content is complete.
\textbf{The stop reason can flag a potentially incomplete tool request even when it passes every
dispatch check.} The runtime must therefore read the stop reason before dispatch. It must refuse
an incomplete request before the tool has any effect, then return an observation that the model
can use to respond to the failure.

Recovering from truncation costs both the original call and the retry. The truncated call ran
and incurred a charge, so accounting settles it as usual. Retrying with a larger output limit
starts a new call. That call needs its own admission check and a reservation that covers the
larger limit.

Admission also applies to model calls made to retry work, revise a plan or provide a final
assessment. If the controller uses the entire budget, no budget remains for assessment, and the
run ends exhausted. In the graph implementation of our planning agent, the validator uses the
same admission check as the other two model nodes. If a patch passes its checks after the
fortieth call, the run ends \demoref{budget\_exhausted} without a verdict. A design that requires
a final assessment sets aside part of the budget for it in advance. Admission then gives the
other roles access to $B$ minus that amount. Our code does not implement this reservation.

Accounting must include every role and every attempt. If it counted only controller calls, the
planner and validator could spend without reaching the limit. If each attempt received a new
budget, the budget would reset after every failed attempt. The settled total must therefore last
for the whole run (\cref{sec:state-lifetimes}), just as the call counter does across the proposed
attempt edge in \cref{sec:control-backedges}. In the graph implementation of our planning agent,
all three model nodes update a shared call counter and usage total. Each model-call event in the
trace identifies the role that made the call. We can therefore use the trace to count calls by
role.

\subsection{Controlled measurement}
\label{sec:budgets-measurement}

To compare the cost of two implementations, we need a common budget and a controlled design.
The scripted comparison described in \cref{sec:events-frameworks} tests whether the
implementations follow the same transition rules for the scripted replies. It does not measure
their behaviour with a live model. A live model's replies depend on the messages each
implementation constructs, so a live comparison measures the model together with the
surrounding agent software, called the \emph{harness}:
``When we evaluate `an agent,' we're evaluating the harness and the model working
together''~\citep{anthropic-evals-agents}. The unit of measurement is a trial.

\begin{definition}[Trial]
\label{def:trial}
``Each attempt at a task is a trial. Because model outputs vary between runs, we run multiple trials
to produce more consistent results.''
\end{definition}

A comparison changes the implementation while keeping other conditions fixed. It repeats each
configuration over several trials. Seven conditions must stay the same.

\bi

\item \textbf{Tasks.} Give every implementation the same alerts in the same test repository.

\item \textbf{Initial environment.} Start each trial from a fresh copy of the same workspace.
This prevents access to files, caches or history from earlier trials only if tools cannot read
outside that workspace. Our tools allow such access through the glob argument of
\demoref{search}, as shown in \cref{sec:boundary-demo}.

\item \textbf{Model configuration.} Use the same model, version, sampling parameters and per-call
output limit.

\item \textbf{Prompts.} Give each role the same system prompts and task messages.

\item \textbf{Tools.} Provide the same tools, with the same signatures, descriptions and limits.

\item \textbf{Acceptance rules.} Use the same checks and validator so that \emph{accepted} means
the same thing for both implementations.

\item \textbf{Budget policy.} Use the same unit, budget $B$, and admission rule. With a call-count
budget, an implementation that makes more calls uses up the budget sooner. Different budget policies could change the
results and make it unclear how much the implementation contributed.

\ei

For each implementation, report how often each terminal outcome occurs across trials. Also report
i) usage by token kind, ii) calls by role, iii) latency, and iv) the exhaustion rate. An acceptance
rate alone leaves unclear whether the other runs were rejected or exhausted their budgets. Usage
alone leaves unclear whether a low-cost run completed the task or stopped early.

A fixed seed does not ensure that two runs follow the same sequence of steps. It fixes how the
sampler draws from a distribution for a given input, while the input depends on the
implementation. If two implementations format messages differently, the model receives different
inputs from the first call. A difference in one tool result also changes all later messages.
Whether identical requests produce identical outputs depends partly on how the provider serves
them, which the seed does not control. Our planning agent uses seed 0 and temperature 0. These
settings fix the sampler's configuration but do not determine the sequence of steps in a run.
Repeated trials let us measure differences between implementations.

The results support conclusions about the implementations, model, prompts, tasks and budget
tested. They do not establish which implementation would perform better with another model or
budget. Another model may respond differently to the same messages, and another budget changes
where runs stop. A small number of trials may also be insufficient to distinguish a real
difference from ordinary variation between runs.

\paragraph{Looking ahead.} We have described each agent decision by naming the component that
makes it and the artifact that records it. A routing function selects the next location, and a
routing event records the choice. The dispatcher permits or refuses a tool request, and an
observation records the result. Admission permits a call, and accounting records its cost. The
runtime sets the terminal status, and the trace records it. HW1 asks you to describe your agent
in the same way. For each decision, identify the responsible component and the artifact that
provides evidence of the decision. A reviewer needs both to check what occurred.

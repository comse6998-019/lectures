This edition assumes the common words of computing, such as operating system, file and port. One matters throughout: a process is a running program.

An agent is a language model joined to a program. The language model, the model for short, chooses each next action and writes it as text. The program carries the action out.

OpenShell is NVIDIA's open-source system for running agents under enforced limits. It runs the agent's program inside a sandbox, an environment that limits what the processes inside it may do.

Each chapter answers one question. It draws the mechanism in the abstract first. It then shows the mechanism at work in Cyberbird, the course's own agent. Every OpenShell and Cyberbird term is defined where it first appears.

1What an agent needs, and who answers

Every action an agent takes is a request to the operating system. This chapter follows those requests to the parts of OpenShell that answer them.

1.1The question this chapter answers

This chapter asks what an agent requests from the machine, which part of OpenShell answers each request, and where a request can be refused.

1.2Files, processes and connections

The program performs each action the model chooses, running as one or more processes. Each process asks the operating system's kernel for everything it uses. The kernel is the part of the operating system that controls files, processes, memory and the network. A request from a process to the kernel is a system call. A process's authority is the set of system calls the kernel will carry out for it.

An agent needs the machine for files, processes and connections (Figure 1).

  • Files. The agent reads the code it works on and writes its changes, with open(), read() and write(). Some files, such as a secret key, it must never read.
  • Processes. The agent starts programs such as a shell, Python or a scanner. It calls fork() to create a process and execve() to load a program into it. Each new process is a child of the agent and inherits its authority.
  • Connections. The agent calls connect() to reach its model's API, the network service that runs the model.

The kernel sees every one of these requests as a system call. A check inside the agent's program covers only the code that calls it, and a bug or a new tool can skip it. A rule held by the kernel applies to every process. OpenShell therefore enforces its rules at the kernel. The kernel applies a rule itself, or pauses the call and asks a part of OpenShell outside the agent.

In Cyberbird's case, the agent works on one alert from Bandit, a scanner that reports likely security flaws in Python code. The alert marks a possible SQL injection, user input that can rewrite a database query, at line 46 of testcode/BenchmarkTest00283.py. That file belongs to Cyberbird's fixture, its pinned copy of the OWASP Benchmark for Python. The benchmark is a set of small programs, each labelled vulnerable or safe. The model chooses each step as a tool call, a request to run read_file, search or edit. Figure 2 shows Cyberbird's needs.

  • Files. Cyberbird copies the fixture's src/ folder into a workspace under /tmp. Its tools read the case, search helpers/ and edit the copy.
  • Processes. The agent is a Python process. It starts bandit to scan the fixture. When the model stops calling tools, Cyberbird submits its change. It then starts patch to check that the change applies and bandit to scan the file again.
  • Connections. Every step calls the model server named by its --model option.

Cyberbird also withholds files from the model. Its workspace code moves the other benchmark cases, such as BenchmarkTest00284.py, out of the copy. The answer key, ground-truth/expectedresults-0.1.csv, labels every case. It sits beside src/ and is never copied.

1.3The parts of OpenShell that answer

OpenShell divides the work of answering among separate components (Figure 3). The paragraphs below read it one component at a time.

Client. The client is the tool a person uses to manage sandboxes: the openshell command line, a terminal dashboard or a programming library. It sends management requests, such as "create a sandbox". It plays no part in what the agent does.

Gateway. The gateway is OpenShell's management service. It checks who is calling and keeps a durable record of every sandbox. It also stores each sandbox's policy: the rules for which files its processes may read or write and which destinations they may reach.

Compute driver. The compute driver turns the gateway's record into running resources. It can use Docker or Kubernetes, two systems that run containers, groups of processes with their own view of files and network. It can also use a virtual machine, a simulated computer with its own kernel. It creates separate environments for the agent and for the OpenShell program that supervises it. Where each one runs, and how the two are kept apart, is their placement.

Agent and tools. The agent and every process it starts form the workload. OpenShell treats the workload as untrusted, because any code in it may be faulty or hostile. The dashed box labelled "Untrusted workload" holds these processes and also one OpenShell program.

Sandbox runtime. The sandbox runtime is that OpenShell program. It starts the agent. Before the agent's first instruction, it reduces the agent's authority and installs kernel rules that limit which files a process may open. When a process calls connect(), the kernel pauses the call, and the runtime passes it out for a decision. Chapter 2 explains why OpenShell can rely on it.

Trusted supervisor. The supervisor is OpenShell's program outside the dashed box. It holds the policy's network rules and the real credentials, the keys and tokens that services accept as proof of identity. It is trusted because the agent's code cannot reach it, so it decides every connection and opens the permitted ones itself.

The runtime and the supervisor talk over the authenticated runtime channel, a private connection on which each side proves its identity. TLS, the protocol behind HTTPS, encrypts it. The supervisor also opens its own link to the gateway, the supervisor-initiated control session, and receives the policy and credentials through it.

Approved external service. An approved external service is a destination the policy permits, such as a model's API. The supervisor opens the connection and relays the traffic. Every destination the policy leaves out stays unreachable.

What "placement" means

Placement is where the compute driver runs the workload and the supervisor, and how it keeps them apart. On Docker, they run in two containers. Containers share the kernel of the machine they run on, the host. The workload's container has no network. The supervisor's container uses the host's network. A private, authenticated connection joins the two.

On Kubernetes, each side gets its own Pod, a group of containers scheduled together. On the virtual-machine driver, the workload runs inside the virtual machine and the supervisor on the host. Each arrangement keeps the supervisor and its credentials out of the workload's reach.

1.4Cyberbird inside OpenShell

Figure 4 redraws Figure 3 for Cyberbird's sandbox on Docker inside Colima, which runs Docker's Linux virtual machine on a Mac. Its policy is the narrowed one of the worked example below. The course's own Cyberbird policy is broader.

  • The gateway keeps the record named cyberbird and its policy.
  • The compute driver, Docker, places Cyberbird's container, which has no network, beside the supervisor's.
  • The workload is the cyberbird Python process with its bandit and patch processes.
  • The supervisor admits one program, python3.12, to one destination, the model server. That server is the approved external service.

1.5Worked example: the withheld case and the answer key

Inside the container, Cyberbird's repository sits at /app. Suppose the model asks read_file for two files it must not see. The first is the withheld case testcode/BenchmarkTest00284.py. The second is the answer key, /app/fixtures/owasp-benchmark-python/ground-truth/expectedresults-0.1.csv. The requests meet four layers in turn.

  1. The model. A tool call is text, and text opens no file.
  2. Cyberbird's own code. Cyberbird's dispatcher, the code that runs each tool call, passes every path through resolve(). The withheld case is absent from the copy, so the first call returns no such file. The answer key lies outside the workspace, so the second returns a refusal.
  3. The gap. Both refusals are Python code inside the agent's process. A tool that skipped resolve(), or any other program in the sandbox, would send its open() straight to the kernel. The course tested this gap with cat, run inside the sandbox through openshell sandbox exec.
  4. The kernel. Before Cyberbird started, the sandbox runtime turned the policy's file lists into Landlock rules. Landlock is a Linux feature that limits the files a process and its children may open. The kernel answers every open() from those rules.

The course's Cyberbird policy listed all of /app as readable. A listed folder grants every file below it, so cat printed the key's first line. The narrowed policy listed only Cyberbird's code, its Python environment and the fixture's src/ folder. The ground-truth/ folder was on no list, and the kernel refused the read:

$ cat /app/fixtures/owasp-benchmark-python/ground-truth/expectedresults-0.1.csv
cat: /app/fixtures/owasp-benchmark-python/ground-truth/expectedresults-0.1.csv: Permission denied

Under the narrowed policy, Cyberbird still fixed its alert in eight model calls. The withheld case stayed readable under both policies, because it lies inside src/. Only Cyberbird's own code withholds it.

HW2, the course's second assignment, ships an example policy built the same way. It leaves the answer key off every list, so the HW2 sandbox refuses the key with the same Permission denied.

The supervisor never saw the two file requests, because neither asked for a connection. A model call takes the other path in Figure 4. The kernel pauses Cyberbird's connect(), and the supervisor checks the destination, the port and the calling program. The same call from curl fails, because the policy names only python3.12.

The kernel answers each file request from the runtime's rules, which every child process inherits. The supervisor answers each connection after the kernel pauses it. The gateway and the driver answer only management requests.

Exercise. Under both policies, the kernel let any process read the withheld case. Why can no policy for this run withhold it, and what would have to change?

Cyberbird reads all of src/ inside the sandbox. Bandit scans it at the start, the workspace copies it, and submit copies it again to check the patch. The kernel's rules are fixed for the whole sandbox, so they cannot allow those reads and refuse a later read by a tool.

The scan would have to run before the sandbox starts, and both copies would take only the files the model may see. The policy could then list only the flagged case and the helpers it imports. A policy may name single files as well as folders. The kernel would then refuse every other case, whatever tool asked.

4Demonstration: an MCP server and the MCP Inspector

Fifteen minutes live on the patch agent's edit server, then the debrief and the Inspector's own vulnerability. The Inspector plays the role of host: it shows exactly what a model would be shown.

4.1The Inspector is a host with no model.

  • The MCP Inspector is the project's reference tool for testing and debugging MCP servers: a web client with a Node backend, plus a command-line and a terminal mode, in one package.
  • The backend starts stdio servers and holds every connection. It binds to 127.0.0.1:6274, prints a session token at launch, and puts the token in the URL it opens; every API route requires it.
  • One command starts it with the course server loaded: uv run --with "mcp[cli]" mcp dev server.py.
  • In the terms of slide 16, the Inspector is a host with a browser as its user and no model. What it displays is what the model would be shown.

Takeaway. Every request the Inspector sends is a request a real host's client would send after the model chose the call.

Notes. Inspector 2.9.0 (September 30, 2026), Node 22.19 or later; checked on October 7. The mcp dev command needs the cli extra and connects in the previous protocol era (2025-11-25), so the log opens with an initialize handshake; the same server answers the 2026-07-28 revision when a client asks for it (slide 46). The token is MCP_INSPECTOR_API_TOKEN; DANGEROUSLY_OMIT_AUTH disables it, and slide 4.4 explains why the token exists. The v1 line of the Inspector receives security fixes only.

4.3The Inspector displays the contract unchecked.

  • One channel for failure was on the screen. A result marked isError reaches the model, with the server's reason. The other channel, a JSON-RPC error that reaches the client's code, is slide 25.
  • Timeouts are per hop and unbudgeted. A cancelled request is a stopped wait, and the tool keeps running.
  • The description is text, and the model will read every word of it. The Inspector showed the poisoned sentence and flagged nothing.
  • A changed implementation under an unchanged description is invisible at this layer.

Takeaway. Everything a host can see about a tool before running it was on the screen. Everything it cannot see is the subject of the rest of the lecture.

4.4The Inspector itself had a critical flaw.

  • CVE-2025-49596, reported by Oligo Security, CVSS 9.4[1]. Versions of the Inspector below 0.14.1 had no authentication between the web client and the backend proxy. An unauthenticated request could launch MCP commands over stdio, which is remote code execution.
  • The weakness class is CWE-306, Missing Authentication for Critical Function. Oligo's exploit chained it with the 0.0.0.0-day browser quirk and a cross-site request from a public web page, so visiting a malicious page was sufficient; DNS rebinding was an alternative route in.
  • The fix added a session token and origin checks, and bound the backend to localhost. A similar flaw, CVE-2026-23744 (CVSS 9.8), was later found in MCPJam, a third-party inspector that listened on 0.0.0.0[2].

Takeaway. The debugging tool is itself a host with a trust boundary: the same five operations, the same two parties that must not trust each other, and the same consequence when one check is missing.

Notes. GitHub advisory GHSA-7f8r-222p-6f5g, published June 13, 2025. NVD gives CVSS 9.4; several databases give 9.6. CVE-2026-23744: MCPJam inspector 1.4.2 and earlier, fixed in 1.4.3; its /api/mcp/connect route executed the command and arguments in a request without checks.

5The top of the ladder: OWASP MCP Top 10 and MITRE ATLAS

The weakness ladder as the lead-in; the two catalogues at its top rung; then ATLAS: what it is and how its agentic coverage grew, and the techniques whose target is a tool, a tool's credentials, a tool's egress path, or the sandbox the tool runs in. smell→fault→weakness (CWE)→vulnerability (CVE)→threat (OWASP MCP Top 10, ATLAS)

5.1A threat is an attacker's use of a vulnerability.

  • A smell is a design symptom.
  • A fault is a defect that produces wrong behavior at run time.
  • A weakness is a class of fault, catalogued by the Common Weakness Enumeration (CWE).
  • A vulnerability is a reported instance in a product, catalogued as a CVE.
  • A threat is the action an attacker takes with it, catalogued by ATLAS.

Takeaway. From the demonstration, one rung at a time: a local backend that accepts a connection from any caller (smell); the backend launches a server process for an unauthenticated request (fault); CWE-306 (weakness); CVE-2025-49596 (vulnerability); a web page the developer visits launches commands on the developer's machine (threat).

Notes. The lower rungs describe the defect. The top rung describes the adversary's use of it. Lecture 4's guarantees table is the ladder read from the defender's side: each unenforced row is a weakness waiting for a vulnerability.

5.3–5.4Two thirds of ATLAS is now about agents. (merged)

  • MITRE ATLAS, the Adversarial Threat Landscape for Artificial-Intelligence Systems, is MITRE's knowledge base of adversary tactics and techniques against AI-enabled systems, modeled on ATT&CK[1].
  • A tactic is the adversary's goal at one stage of an attack: sixteen, from Reconnaissance to Impact. A technique is a method for achieving a tactic (AML.T0000), refined by sub-techniques (AML.T0000.000). A mitigation is a countermeasure mapped to techniques (AML.M0000). A case study is a documented incident mapped to the techniques it used (AML.CS0000).
  • Each technique carries a platform tag (Agentic AI, Generative AI, Predictive AI, Enterprise) and a maturity: Realized, observed in a real incident; Demonstrated, shown by researchers; Feasible, judged possible.
  • The agent coverage is recent. Fourteen agent techniques entered on September 30, 2025 (context poisoning, configuration tampering, credential harvesting, tool discovery, exfiltration through tool invocation). Escape to Host and the Cursor MCP case study followed on January 30, 2026, the OpenClaw case studies on February 6, AI Agent Tool Poisoning on March 30, and its three sub-techniques on July 31.
  • Release 2026.09 (September 15, 2026): 120 techniques and 88 sub-techniques, 208 entries; 16 tactics, 40 mitigations, 73 case studies. 139 of the 208 entries carry the Agentic AI tag: 57 Realized, 62 Demonstrated, 20 Feasible. 125 of the 208 were created in 2025 or 2026.

Takeaway. Two thirds of the matrix is about agents, and three fifths of it is less than two years old.

Notes. No technique is named for MCP. MCP servers are named in the descriptions of six techniques (AML.T0002.002, T0010.005, T0016.004, T0017.002, T0110, T0111) and in three case studies: AML.CS0045, Data Exfiltration via an MCP Server used by Cursor; AML.CS0053, Poisoned Postmark MCP Server Email Exfiltration; AML.CS0054, Data Exfiltration via Remote Poisoned MCP Tool. ATLAS implements no defense: it records that an attack exists. Its identifiers change between releases, so cite the release used.

6From catalogue to enforcement point

Evidence that the model itself is a weakening enforcement point once tools are in the loop; the four processes in which a rule can be enforced; and the point at which each technique enters the three-party diagram.

6.1Tool use alone weakens the model's refusals.

  • Takehi et al. (2026) compare the same multimodal models with and without tool use on three safety benchmarks, MM-SafetyBench, VLSBench and HoliSafe. The agentic condition follows the ReAct loop with four tools: tagging, zoom, OCR, and a sandboxed Python interpreter. The metric is the refusal failure rate (RFR): the share of harmful requests the model fails to refuse[1].
  • Every one of eleven models fails to refuse more often with tools than without, on every benchmark. The average increase is 5.7 points, a relative increase of 17.7%; the largest relative increase is 68.7%. Open-weight models move from 40.7 to 47.7; proprietary models from 22.1 to 26.3. Claude Opus 4.6, the safest model without tools, moves from 13.6 to 18.1.
  • The effect grows with the number of tool calls. Among requests the no-tool model refused, the agentic model's RFR is near zero when it calls no tool and rises with one, two, and three or more calls.
  • Tool content is not the cause. A "fake zoom" that returns the original image produces the same RFR as a real zoom (34.2 against 34.0). The prompt is not the cause: a minimal prompt gives +3.8 and the structured prompt +4.2. The harness is not the cause: Gemini-3-Flash's native Agentic Vision mode, with tools the authors do not control, degrades by 15.2 points.

7OpenShell: enforcement outside the agent's process

What NVIDIA OpenShell is, how it is built, what its four policy layers enforce, what it deliberately leaves out, and which ATLAS techniques it addresses. Theory and documentation only; nothing is run. Every claim is checked against the source checkout at commit be7af99 (October 2026).

7.1OpenShell runs an unmodified agent in a sandbox.

  • NVIDIA OpenShell is an open-source runtime, Apache 2.0, that runs an AI agent inside a sandbox and enforces, from outside the agent's process, what the agent may read, run and connect to, and which credentials it may use[1].
  • Announced at GTC on March 16, 2026, as part of NemoClaw, the stack that runs OpenClaw inside it. On September 28, 2026, release 0.1.0 was paired with Sentry as the Open Agent Safety Platform[2].
  • Agents run unmodified. The documentation's examples are Claude Code, OpenCode, Codex and GitHub Copilot CLI, each in a container image the operator supplies.
  • One agent, one sandbox: openshell sandbox create --name demo --from registry.example.com/team/claude-code:1.0 -- claude.

Takeaway. The rule moves from rows one and two of slide 6.2 to row three, with a supervisor process holding the part that changes at run time.

Notes. Version 0.1.3 is in pre-release at the checkout. NVIDIA's stated motivation at the September launch: agents in several published incidents circumvented application-layer controls to complete their task. No peer-reviewed evaluation of OpenShell exists as of October 2026.

7.2Gateway, supervisor and sandbox divide the work.

  • Gateway. The control plane. It manages the lifecycle and policies of many sandboxes, stores credentials, and admits configuration changes.
  • Supervisor. Runs outside the sandbox. It holds the policy and the credentials, decides every outbound connection, inspects requests, and connects the sandbox to the gateway.
  • Sandbox. The isolated runtime in which the agent runs, with a small sandbox runtime inside it that launches processes and reports their network attempts.
  • Substrates: Docker, Podman, Kubernetes, a libkrun microVM, or Windows isolation. The substrate isolates; OpenShell adds the agent-specific control.

Takeaway. Compare slide 16: the gateway is to sandboxes what the host is to clients. The supervisor is lecture 4's dispatcher, moved out of the agent's process.

Notes. Kubernetes relies on its network plugin to enforce the egress fence; the microVM driver is experimental. Figure: the OpenShell guide's Figure 1, rendered in the deck's figure style (slides/figures/openshell/architecture.png).

7.4Credentials never enter the sandbox.

  • Providers are named credential bundles configured at the gateway: openshell provider create --name anthropic --type anthropic --from-existing.
  • The agent receives a placeholder. When a request leaves the sandbox for an authorized endpoint, the supervisor substitutes the real credential. Requests to other endpoints never see it.
  • Consequence: AML.T0083, Credentials from AI Agent Configuration, has nothing to read in the sandbox, and exfiltrating the key through a tool call (AML.T0086) fails because the key is not present to exfiltrate.

Takeaway. Lecture 4's dispatcher supplied the workspace root because the model could not be trusted to. The supervisor supplies the key for the same reason.

Notes. Guide section 11.2; docs/how-it-works/providers/profiles.mdx calls it an opaque workload placeholder. The credential's authority remains: an agent can still make any allowed request with it, so narrow endpoint rules and narrow upstream permissions are still needed. 7.5A policy is a YAML document the gateway validates.

  • A policy has sections for each layer: filesystem_policy, landlock, process, network_policies, network_middlewares.
  • The filesystem and process sections are read once, at creation. Network rules can be reloaded on a running sandbox.
  • A network rule names binaries and endpoints. The quickstart's rule lets curl reach api.github.com on port 443 with the read-only preset (GET, HEAD, OPTIONS) and enforcement: enforce; without that line the mode is audit, which logs a violation and lets the request through.
  • When policy blocks a request, OpenShell records the denial, and the agent can propose a narrow rule that an operator, or an automatic rule, approves. Release 0.1.0 added a prover that checks a policy against a boundary policy with an SMT solver.

Takeaway. The denial record is the accounting half of lecture 4's budget slide. The approval is the admission half.

8What the research says about sandboxes

The 2026 preprint cluster on agent sandboxes: escapes, kernel primitives, capabilities, and what remains open. Slide 8.4 (Crab) is cut; checkpointing returns in week 9.

8.1A container is a namespace.

  • SandboxEscapeBench (March 2026) measures whether frontier models can exploit seeded vulnerabilities to escape nested OCI containers: misconfiguration, privilege mistakes, kernel flaws, orchestration weaknesses. When vulnerabilities are present, the models find and exploit them[1].
  • The benchmark covers Docker and OCI engines only. gVisor, Firecracker and libkrun have no equivalent agent benchmark yet.
  • Across five sandbox products, engine-side patches for coordinated disclosures land in about zero days, while downstream lag spans 0 to 471 or more days[2].

Takeaway. The question is which kernel mechanism carries the policy, and how quickly its fixes reach the product.

Notes. Quantifying Frontier LLM Capabilities for Container Sandbox Escape, arXiv:2603.02277 (v3, August 2026). The patch-lag figure is from the comparative study on slide 8.5.

8.2Sandlock writes the threat model down.

  • Sandlock (May 2026) compiles static, input-independent policy into Landlock and seccomp-bpf, and runs a narrow supervisor over seccomp user notification for decisions that depend on run-time state[1].
  • It adds a programmable run-time policy function, HTTP-level access control, and reversible filesystem effects, at about 5 ms of startup overhead and bare-metal Redis throughput. It needs no root, no cgroups, no images. It is open source.
  • Trusted: the host kernel and the supervisor. Out of scope: kernel vulnerabilities, side channels, privileged local attackers.

Takeaway. OpenShell's locked layers, published with the assumptions written down.

Notes. Wang and Zheng, Sandlock: Confining AI Agent Code with Unprivileged Linux Primitives, arXiv:2605.26298; Agentic OS Workshop at ASPLOS 2026. github.com/multikernel/sandlock.

8.3Research now revokes authority after each step.

  • Lingering Authority (June 2026): revocable capabilities for coding agents. Authority granted for one subgoal should not outlive it; PORTICO rejects every post-closure reuse that a non-revoking comparator permits[1].
  • ActPlane (June 2026): agents declare policies, and an eBPF engine enforces them in the kernel with semantic feedback, at 1.9% to 8.4% overhead, covering execution paths that tool-call interception cannot see[2].
  • AgentKernel (August 2026): "current governance stacks remain application-level middleware that share a process trust boundary with the agents they monitor." Its answer is a mandatory boundary with kernel-level allowlists and taint-aware memory[3].
  • The finding they respond to: production scope is expand-only, with nothing that shrinks it (slide 6.2).

Takeaway. Stronger walls are the premise. The research question is how authority is granted and taken back.

9Synthesis

The action, the asset, and the enforcement point; the poll again; what comes next.

9.1The runtime must sit where the agent cannot reach.

  • The contract has five parts. Two are enforced by the protocol. The fifth, execution constraints, is enforced only by the process the tool runs in.
  • ATLAS describes the adversary's action and the asset it acts on: the definition text, the implementation, the response, the stored credential, the outbound connection, the kernel boundary.
  • The runtime determines the enforcement point for each asset: the host for text, the kernel for code and files, the supervisor for connections and credentials.
  • A rule enforced inside the agent's process can be disabled by the agent. A rule enforced outside it cannot be disabled without compromising the enforcing process.
  • A rule enforced only in the model's alignment weakens as the tool loop runs, with no adversary present (slide 6.1). The model cannot be the enforcement point for its own tool use.

Takeaway. Last week: the guarantees are supplied by the contract and the runtime. This week: the runtime must execute in a process the agent cannot modify, and it cannot be the model.

Glossary

Host, client, server
In MCP, the application that contains the model loop; the component inside it that holds one connection to one server; and the separate program that exposes and executes tools.
MCP Inspector
The reference developer tool for testing MCP servers: a web client with a Node backend that connects to servers over stdio or HTTP, plus command-line and terminal modes.
Protocol error, tool execution error
A failure of the request or the server, returned to client code as a JSON-RPC error; and a failure of the tool's work, returned to the model as a result marked isError.
Tactic, technique, sub-technique, mitigation, case study
In ATLAS: an adversary's goal; a method with a stable identifier; a refinement of a method; a mapped countermeasure; a documented incident mapped to techniques.
Realized, Demonstrated, Feasible
ATLAS maturity ratings: observed in a real incident; shown by researchers; judged possible.
Tool poisoning
Introducing or modifying malicious content or behavior in a tool's definition, implementation, or runtime responses. ATLAS AML.T0110 and its three sub-techniques.
Rug pull
Publishing a legitimate component, gaining adoption, then pushing a malicious update. ATLAS AML.T0109.
Context poisoning
Causing instructions to be stored in an agent's memory or to persist in a thread so that behavior changes outlast the injection. ATLAS AML.T0080.
Escape to host
Breaking out of a container or virtualized environment to the underlying host. ATLAS AML.T0105, derived from ATT&CK T1611.
Smell, fault, weakness, vulnerability, threat
A design symptom; a run-time defect; a class of fault (CWE); a reported instance (CVE); the action an attacker takes with it (OWASP MCP Top 10, ATLAS).
Landlock
A Linux security module that lets an unprivileged process restrict its own and its children's access to files, enforced by the kernel.
seccomp
A Linux mechanism that filters which system calls a process may make; with user notification, a supervisor can decide a paused call.
Namespace, container, microVM, user-space kernel
Isolation substrates in increasing order of separation: Linux namespaces; a container built on them; a lightweight virtual machine with its own kernel (Firecracker, libkrun); an intercepting kernel in user space (gVisor).
Egress policy
A rule set governing which programs may reach which network endpoints, methods and paths from a sandbox; deny by default in OpenShell.
Provider credentials, placeholder
In OpenShell, credentials held by the gateway and supervisor; the agent sees an opaque placeholder that the supervisor replaces only in requests bound for authorized endpoints.
DPU
A data processing unit: a processor in the network path, separate from the host CPU. Sentry runs on NVIDIA BlueField-4 DPUs.
Admission, accounting
The decision before a call whether it may start; the record after a call of what happened.
Refusal failure rate (RFR)
The share of harmful requests a model fails to refuse, from 0 to 100; higher is less safe. Takehi et al. (2026).
Context dilution, safety focus displacement
Two proposed mechanisms for refusal failure under tool use: the original request loses salience as tool observations accumulate; and the model opens its answer by describing tool observations instead of addressing safety.

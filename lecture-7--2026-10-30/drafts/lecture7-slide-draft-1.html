1Reconstruct the execution boundary

Make the components and their jobs clear before asking students to read YAML.

1.1Where a forbidden read is stopped

  • The model produces Python that opens the answer key.
  • The harness executes that Python inside the sandbox.
  • The program requests a file from the operating system.
  • Opening poll: which component can refuse that direct file read?

Takeaway. Generated code eventually requests an operating-system operation.

Notes. Offer the system prompt, dispatcher, kernel policy, and image as choices. The intended answer is the kernel policy, assuming the image contains the file and its ordinary permissions admit the read. A dispatcher only mediates operations that pass through it. Withholding the file from an image is another valid design, so state that the file exists in this example. Return to the poll during the direct probe.

2Read and write the policy

Connect every permission to a program operation, then predict what will happen in the live example.

2.1Filesystem grants include descendants

filesystem_policy:
  include_workdir: true
  read_only: [/bin, /usr, /lib, /lib64, /etc, /proc,
              /dev/urandom, /app,
              /target/testcode, /target/helpers, /target/app.py]
  read_write: [/sandbox, /tmp, /dev/null]
landlock:
  compatibility: hard_requirement
  • A listed directory grants access to files beneath it.
  • Listing selected code directories leaves the answer key outside the grant.
  • hard_requirement makes unavailable enforcement a startup failure.

Takeaway. Draw the directory tree before granting its parent.

Notes. This excerpt comes from the HW2 example; it is only the filesystem portion of a policy. The answer key can exist in the image and remain unreadable inside the sandbox. In the older Cyberbird image, /app also contains the fixture and key, so granting that whole tree exposes them. In the HW2 layout, /app holds application dependencies and the target lives separately. Explain the directory layouts alongside the YAML. The writable sandbox and temporary directories also need explanation; the target's original files remain outside those writable trees. HW2, access rules and enforcement.

Build: code directories and answer-key sibling as a tree. First reveal the broad grant and all descendants; then reveal the selected-directory grants. Split the YAML across builds at 11 pt in the eventual deck.

2.2Network rules name programs and endpoints

network_policies:
  model_provider:
    endpoints:
      - host: host.lima.internal
        port: 8080
        protocol: tcp
    binaries:
      - path: /usr/local/bin/python3.12
  • The program, destination, and port must match an allowed request.
  • The same destination requested by another program can be refused.
  • The same program requesting another destination can be refused.

Takeaway. Predict the caller and destination together.

Notes. This is the course's Colima/local-model pattern, with a tcp endpoint. The hostname is specific to that setup. The cloud example instead uses a rest endpoint with explicit enforcement: enforce and an access preset that permits POST. Keep the two schemas distinct. The captured local run admits Python and refuses curl to the model endpoint. Read the logged reason before attributing a connection error to policy. Feasibility record; local policy example.

Build: source executable → destination:port. Ask the room to predict Python/model, curl/model, and Python/unlisted-site before revealing the policy decisions.

2.3Providers supply credentials upstream

  • The provider attachment keeps the real cloud key outside the workload.
  • The workload receives a placeholder used on its permitted request path.
  • The supervisor supplies the real credential for the authorized provider.

Takeaway. Credential storage and request permissions need separate decisions.

Notes. Two minutes. Reuse the credential-substitution figure and state the consequence: the workload can still make permitted requests using the attached authority. Endpoint restrictions and upstream account permissions remain relevant. The live local-model example needs no cloud key. For a cloud provider, inspect the additional provider network grant in the effective policy. Never print a real key during the demonstration. HW2, model-provider setup; Lecture 6 slides 159–169.

Build: placeholder on the workload side, real credential outside, substitution at the supervisor. Give the provider path one figure and keep the local demonstration's path labelled separately.

2.4Inspect the effective permissions

  • Read the policy written by the team.
  • Inspect baseline and provider additions with policy get --full.
  • Test a permitted operation and a forbidden operation.
  • Use process errors for file probes and denial logs for network probes.

Takeaway. Check the effective grant and the observed operation.

Notes. The recorded setup adds baseline paths and may add a provider policy. The filesystem refusals in the course captures do not appear in the network log; use the program's permission error and a controlled comparison. 5The objectives of context management

Define the object being managed and the competing objectives before introducing methods.

5.1Context supplies one model invocation

  • Instructions and tool definitions describe the task and the available operations.
  • Messages, examples and observations supply the interaction so far.
  • Selected external material supplies documents, source text, search results or other evidence.
  • The system assembles this input before each invocation; some available information stays outside it.

Takeaway. Context management chooses which information reaches each invocation.

Notes. Anthropic's Applied AI team, Effective context engineering for AI agents, September 29, 2025, defines context engineering as curating the tokens supplied during inference. This is a first-party engineering account. Our list organizes its examples for the course. Avoid treating the article's broad explanations of attention or its claims about all models as established universal results.

Build: a request box with four labelled inputs. Keep the surrounding documents visible outside the box.

5.2Useful context serves the next task

  • Task quality: preserve the evidence, constraints and distinctions needed for a sound answer or action.
  • Efficiency: control input length, total token use and elapsed time, including the work of selecting or compressing input.
  • Faithfulness: keep claims supported and preserve conditions that change their meaning.
  • Source access: keep a usable route back to source material when details are needed.

Takeaway. Choose a context policy against explicit task and resource objectives.

Notes. This four-objective formulation is course synthesis. Pan et al., LLMLingua-2, Findings of ACL 2024, §3.1, motivates token reduction, informativeness and faithfulness. Source access is an additional system design objective here. Ask the room what information an accurate one-sentence summary could still omit that a later question would require.

Build: four short objective rows; leave detailed metrics for segment 9.

5.3Capacity and cumulative cost differ

QuantityQuestion it answersConsequence
Context capacityHow much can this invocation accommodate?Plan the input and leave capacity for generation within the model's limits.
Cumulative token useHow much text is processed or generated over all invocations?Repeated history contributes again; compression and retrieval also consume resources.
Latency and monetary costHow long does the full task take, and what is charged?Measure the actual system, including caching and auxiliary calls.

Takeaway. A request can fit while the full run exceeds its budget.

Notes. These are accounting distinctions, with no vendor prices or API assumptions. Token counts alone do not determine charges: caching and different operations can have different prices. Define a course budget explicitly before comparing alternatives.

Build: one bounded request beside a row of repeated invocations. Label the diagrams schematics; use no invented benchmark values.

6What long-context experiments show

Read two controlled studies as evidence about how to evaluate context use.

6.1Evidence position changes performance

  • Liu et al., TACL 2024: vary the position of relevant information in multi-document question answering and key-value retrieval.
  • The reported pattern: performance is often strongest when relevant information appears near the beginning or end, and weaker in the middle.
  • The scope: the finding concerns the models, prompts and tasks evaluated in the study. A present system needs its own measurement.

Takeaway. Test where relevant evidence appears in the supplied context.

Notes. Nelson F. Liu et al., Lost in the Middle: How Language Models Use Long Contexts, Transactions of the Association for Computational Linguistics 12, 157–173, 2024. The controlled tasks and positional results support the slide. The paper's open-domain QA case study also distinguishes retriever recall from reader accuracy: adding retrieved material need not yield proportional answer gains. Do not generalize its numerical results to current models.

Build: the same relevant passage in three positions. Accompany it with the paper's qualitative finding, labelled with study and year; do not invent a performance curve.

6.2Effective context depends on the task

  • Hsieh et al., COLM 2024: RULER extends simple needle retrieval with multiple needles, tracing and aggregation tasks.
  • The reported result: strong simple-retrieval performance coexists with degradation on longer or more demanding test configurations.
  • The scope: these are synthetic tests of the evaluated models. Application success requires application-level tests.

Takeaway. Measure the operations your task requires across the lengths you expect.

Notes. Cheng-Ping Hsieh et al., RULER: What's the Real Context Size of Your Long-Context Language Models?, COLM 2024. The abstract reports 17 models and 13 representative tasks, with drops as context length increases. Keep the distinction between a supported input length and a task-dependent empirical result. RULER measures model context use; it does not directly evaluate an agent compaction policy.

Build: a task table with retrieval, tracing and aggregation. State what must be preserved for each; keep numerical benchmark tables in the reading.

7Four ways to manage context

Distinguish selecting material, fetching it when needed, deleting source tokens and generating a replacement summary.

7.1Retention and retrieval choose material

OperationWhat enters the requestWhat can go wrong
RetainSelected original messages, passages or tool resultsA selection rule can discard a detail the next task needs.
RetrieveMaterial fetched using a query or source referenceThe query can miss evidence; a reference can become stale or inaccessible.

Takeaway. Selection and retrieval determine which source material is available.

Notes. Anthropic's 2025 engineering article, “Context retrieval and agentic search,” describes keeping lightweight identifiers and loading material through tools when required. Its account is practitioner guidance. The failure cases and the retain/retrieve distinction in this table are course synthesis. Retrieval here includes ordinary file and search tools.

Build: two paths from source documents to a request: immediate selection and fetch by reference.

7.2Extractive compression selects tokens

  • Pan et al., Findings of ACL 2024: LLMLingua-2 trains a classifier to preserve or discard source tokens.
  • The method: learn from an extractive compression dataset distilled from an LLM, using bidirectional context to make selection decisions.
  • The evaluation: compare compression with downstream task scores and latency on several datasets.
  • The limit: preserving selected source tokens still requires checking whether the necessary meaning survives deletion.

Takeaway. Evaluate the compressed input through the task it must support.

Notes. Zhuoshi Pan et al., LLMLingua-2: Data Distillation for Efficient and Faithful Task-Agnostic Prompt Compression, Findings of ACL 2024, 963–981. §§3–4 describe distillation and token classification. Evaluations include MeetingBank and several out-of-domain datasets. The last bullet is a course caution inferred from deletion: lexical selection alone supplies no application-specific guarantee. Reported gains are specific to the evaluated configurations; avoid promising a fixed compression ratio or speedup.

Build: a short source passage with selected words highlighted, then the selected sequence. Label it a schematic of extraction.

7.3Abstractive compaction rewrites history

  • Input: selected conversation history or observations.
  • Transformation: generate a shorter account of the information needed to continue.
  • Replacement: assemble subsequent context using that account and any deliberately retained material.
  • Risk: omissions and unsupported statements can change what the next invocation believes.

Takeaway. A generated summary becomes another representation that needs checking.

Notes. Anthropic's 2025 article, “Compaction,” describes summarizing history and continuing with a fresh context. It warns about aggressive loss and recommends evaluating on complex traces. This is an engineering account rather than a controlled comparison of compaction methods. LLMLingua-2 also discusses omitted details and hallucination during generated compression. The four-method taxonomy is the course's organizing scheme.

Build: retain, retrieve, extract and rewrite in one comparison figure. Keep the distinction between obtaining material and transforming its representation explicit.

8Compaction as a design procedure

Turn the objectives into a procedure and inspect exactly what an illustrative summary preserves.

8.1A compaction policy specifies choices

  1. Specify the objective and trigger: which future tasks must the context support, and when should compaction run?
  2. Select the inputs: identify material to retain verbatim, summarize or leave available through references.
  3. Generate the replacement: state facts, decisions, conditions, unresolved questions and source references explicitly.
  4. Check and assemble: test required details, inspect the resulting request and measure the total work.

Takeaway. Specify what the replacement must preserve before compressing.

Notes. This is a proposed engineering procedure, synthesized for the course from the objectives and mechanisms just discussed. Each choice is a policy to evaluate. A token threshold is one possible trigger; task boundaries or changes in information relevance can also motivate a check. Keep durable storage and recovery protocols for next week.

Build: four boxes, with a return arrow from failed checks to selection or generation.

9Evaluating a context policy

Evaluate preservation and resource use together, using questions that expose consequential information loss.

9.1Measure quality and total work

MeasureWhat to inspect
Downstream successCorrect answers or actions on the tasks the context must support.
Evidence preservationRequired facts, exceptions, conditions and usable source references.
FaithfulnessUnsupported additions, changed meanings and unresolved uncertainty presented as settled.
CompressionOriginal and replacement token counts, with the ratio convention stated.
Total workCompression calls, retrieval, downstream calls, latency and actual charges.

Takeaway. Compare task quality at a measured total cost.

Notes. This evaluation rubric is course synthesis. LLMLingua-2 provides a concrete precedent for reporting downstream scores, compression and latency together. Include uncompressed input and a simple selection baseline. Where feasible, compare methods at matched input budgets and report uncertainty across repeated model runs. Compression ratio alone cannot establish that a policy serves its task.

Build: an empty results grid with quality and resource columns. Leave cells blank until measured; no illustrative values that could be mistaken for results.

9.2Stress the details compaction can lose

  • Position and length: move decisive evidence and vary the surrounding material.
  • Conditions and exceptions: ask follow-ups that change when a rule applies.
  • Updates and provenance: introduce a revised source and require the answer to identify its basis.
  • Repeated compaction: check which essential details survive successive replacements.

Takeaway. Build tests around the information your decisions depend on.

Notes. Position and length follow the evaluation logic of Lost in the Middle and RULER. The remaining tests are proposed application tests, with no claimed result from those papers. For the invented example, ask about a routine change after Thursday, an approved emergency fix, and a fix whose approval is unknown. Verify source access separately from summary wording.

Build: three follow-up questions on the invented example, with the supporting clause identified on reveal.

Glossary

Image; sandbox
A packaged filesystem and software environment; an instance running under a policy.
Filesystem grant
Permission to access a listed path and its descendants under the specified mode.
Effective policy
The permissions in force, including runtime baseline and provider additions.
Fixed; per-alert restriction
A rule that holds throughout the run; a rule whose decision depends on the current alert.
Model context
The information included in a particular model invocation, including its instructions, conversation, tools, and selected evidence.
Context window
The model/API's capacity constraint for a request, with the applicable output and other token accounting rules.
Working set
The subset of available information selected for the next invocation.
Retrieval
Loading source material in response to a current information need.
Extractive compression
Reducing an input by retaining selected parts of its existing text.
Abstractive compaction
Replacing accumulated material with a generated account that preserves the information needed for continuing the task.
Provenance
The identity and version of the evidence supporting a retained statement.
